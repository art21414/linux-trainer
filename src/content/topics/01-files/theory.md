# Файлы и каталоги

Всё, с чем работает сервер, лежит в файлах: конфиги, логи, программы, базы. Даже устройства, сокеты и процессы видны как файлы. Поэтому `ls`, `cp`, `mv` и `rm` — большая часть ежедневной работы. И именно в них ошибаются люди с опытом: копия ложится внутрь копии, `rm *` сносит не то, после удаления лога место на диске не освобождается, а `ls -lu` почему-то «не сортирует».

Глава идёт от азов к устройству. Сначала дерево каталогов и пути, потом разбираем `ls -l` по колонкам и выясняем, что такое файл на самом деле (inode). На этом фундаменте — создание и чтение файлов, шаблоны, копирование, удаление, ссылки и три времени файла. В финале — сценарии из жизни сервера: место не освободилось, кончились inode, разреженные файлы, оборванный `mv`. Тему знаешь — прыгай в нужную подтему или сразу в шпаргалку.

**Сквозной пример.** Сервер `server1` на Rocky Linux 9. Приложение живёт в `/srv/app` на XFS, каталог логов принадлежит alice — от её имени работает приложение. Под бэкапы подключён отдельный диск с ext4, он смонтирован в `/backup`. Схема (это не вывод команды, а рисунок):

```text
/srv/app
├── app.conf
├── .env
├── run.sh
├── current -> releases/v2
├── logs/
│   ├── app.log
│   ├── app.log.1
│   ├── app.log.2.gz
│   └── error.log
└── releases/
    ├── v1/   (bin/, conf/)
    └── v2/   (bin/, conf/)
```

**Как читать примеры.** Команды выполняются от root, если не сказано иное; приглашение сокращено до `$`. У root в RHEL есть алиасы `rm -i`, `cp -i` и `mv -i`; в примерах они не действуют, а разобраны в подтеме про cp. Вывод снят в Rocky Linux 9 с локалью `en_US.UTF-8`.

## Дерево каталогов и пути {#paths}

В Linux одно дерево каталогов с корнем `/`. Букв дисков нет: второй диск, раздел или сетевой ресурс **монтируется** в какой-нибудь каталог и дальше выглядит как его часть. У нас `/backup` — отдельный диск, но для `ls` и `cp` это обычный каталог. Граница между файловыми системами (ФС) не видна, пока не попробуешь сделать через неё жёсткую ссылку или `mv`. К этому мы ещё вернёмся.

### Что где лежит

Раскладку описывает стандарт FHS (Filesystem Hierarchy Standard), RHEL следует ему со своими поправками. Главное:

| Каталог | Что там | Что важно на практике |
|---|---|---|
| `/etc` | конфиги системы и сервисов | текст; бэкап перед правкой |
| `/var` | меняющиеся данные | растёт; часто отдельная ФС |
| `/var/log` | логи | место кончается здесь первым |
| `/var/lib` | состояние сервисов | базы, `/var/lib/containers` |
| `/usr` | программы, библиотеки, man | ставят пакеты, руками не править |
| `/usr/local` | собранное вручную | пакеты сюда не пишут |
| `/opt` | сторонний софт целиком | `/opt/<вендор>` |
| `/srv` | данные, которые сервер отдаёт | сайты, файлы, репозитории |
| `/home` | домашние каталоги | `/root` — отдельно, не здесь |
| `/tmp` | временные файлы | чистится через 10 дней |
| `/var/tmp` | временные, переживают перезагрузку | чистится через 30 дней |
| `/run` | PID-файлы, сокеты сервисов | tmpfs в памяти, очищается при каждой загрузке |
| `/boot` | ядро, initramfs, конфиг GRUB | обычно отдельный раздел |
| `/dev` | файлы устройств | `/dev/sda`, `/dev/null` |
| `/proc`, `/sys` | интерфейс к ядру и процессам | на диске их нет |
| `/mnt`, `/media` | точки монтирования | временное и съёмное |

Пустой `/afs` в корне RHEL 9 — точка монтирования для сетевой ФС AFS, его можно не замечать.

Четыре «классических» каталога на самом деле ссылки:

```text
$ ls -ld /bin /sbin /lib /lib64
lrwxrwxrwx. 1 root root 7 Nov  3  2024 /bin -> usr/bin
lrwxrwxrwx. 1 root root 7 Nov  3  2024 /lib -> usr/lib
lrwxrwxrwx. 1 root root 9 Nov  3  2024 /lib64 -> usr/lib64
lrwxrwxrwx. 1 root root 8 Nov  3  2024 /sbin -> usr/sbin
```

Это **/usr merge**, он в RHEL с 7-й версии: все программы лежат в `/usr/bin` и `/usr/sbin`, а старые пути оставлены ссылками, чтобы не сломать скрипты с `#!/bin/bash`. Так что `/bin/bash` и `/usr/bin/bash` — один и тот же файл. Это видно по номеру inode в первой колонке `ls -i` (что это за номер — в подтеме про inode):

```text
$ ls -li /bin/bash /usr/bin/bash
566821 -rwxr-xr-x. 1 root root 1389024 Apr 30  2024 /bin/bash
566821 -rwxr-xr-x. 1 root root 1389024 Apr 30  2024 /usr/bin/bash
```

Так же устроены `/var/run -> ../run` и `/var/lock -> ../run/lock`: старые пути ведут в `/run`.

> **На практике.** `/tmp` в RHEL 9 — обычный каталог на корневой ФС, а не tmpfs, как в Fedora: Red Hat отключил это патчем в systemd. Его чистит `systemd-tmpfiles` по правилам из `/usr/lib/tmpfiles.d/tmp.conf`: из `/tmp` удаляется то, что не трогали 10 дней, из `/var/tmp` — 30 дней. Положил в `/tmp` дамп «на месяц» — через две недели его не будет.

```text
$ grep '^[^#]' /usr/lib/tmpfiles.d/tmp.conf
q /tmp 1777 root root 10d
q /var/tmp 1777 root root 30d
```

### Абсолютные и относительные пути

**Абсолютный** путь начинается с `/` и не зависит от того, где ты находишься: `/srv/app/app.conf`. **Относительный** отсчитывается от текущего каталога: из `/srv/app` тот же файл — это `app.conf` или `./app.conf`.

В каждом каталоге есть две служебные записи: `.` — сам каталог и `..` — родительский. Это не синтаксис bash, а настоящие записи каталога (их показывает `ls -a`), поэтому они работают в любой команде: `cp ../app.conf .`. У корня `..` указывает на сам корень: после `cd /..` ты останешься в `/`.

Тильду раскрывает bash ещё до запуска команды: `~` — твой домашний каталог, `~alice` — домашний каталог alice, `~-` — предыдущий каталог.

| Команда | Куда попадёшь |
|---|---|
| `cd` или `cd ~` | домой |
| `cd -` | в предыдущий каталог (и напечатает его) |
| `cd ..` | на уровень вверх |
| `cd ~alice` | в домашний каталог alice, если пустят |

`cd -` выручает, когда скачешь между двумя каталогами. Пример от alice:

```text
$ cd /srv/app/releases/v2/conf
$ cd ../../v1
$ pwd
/srv/app/releases/v1
$ cd -
/srv/app/releases/v2/conf
$ cd -
/srv/app/releases/v1
```

Предыдущий каталог хранится в переменной `$OLDPWD`. Через `~-` его можно подставить в любую команду: `cp app.conf ~-/` скопирует файл туда, откуда ты только что пришёл.

Ошибки `cd` пишет bash, у них префикс `bash: cd:`:

```text
$ cd /srv/app/app.conf
bash: cd: /srv/app/app.conf: Not a directory
$ cd ~bob
bash: cd: /home/bob: Permission denied
```

### Логический и физический путь

`/srv/app/current` — ссылка на `releases/v2`. Зайдём через неё:

```text
$ cd /srv/app/current
$ pwd
/srv/app/current
$ pwd -P
/srv/app/releases/v2
```

bash запоминает, **как** ты пришёл, — это логический путь. `pwd -P` показывает, где ты находишься физически. Подвох кроется в `..`:

```text
$ cd /srv/app/current
$ ls ..
v1  v2
$ cd ..
$ pwd
/srv/app
```

`ls ..` показал содержимое `releases`, то есть физического родителя `v2`. А `cd ..` вернул в `/srv/app`: bash просто отрезал последний компонент логического пути. Для внешних команд (`ls`, `cp`, `rm`) `..` всегда физический. Значит, `cp file ..`, выполненный из `current`, положит файл в `releases`, а вовсе не туда, куда «вернётся» `cd ..`. Если нужен физический переход, есть `cd -P`.

Полный физический путь без ссылок и `..` выдаёт `realpath`:

```text
$ realpath /srv/app/current/..
/srv/app/releases
```

### Что можно в имени

Имя файла — до 255 байт, а не символов: кириллица в UTF-8 занимает по 2 байта на букву. Путь целиком, который ядро принимает в одном вызове, — до 4096 байт (`PATH_MAX`). Запрещены в имени только `/` и нулевой байт. Пробелы, `*`, перевод строки и дефис в начале разрешены, и все они ещё доставят проблем (подтемы про создание и про rm).

```text
$ getconf NAME_MAX /srv
255
```

> **Ловушка.** Лишние слэши — не ошибка: `/srv//app///app.conf` — тот же путь. Отсюда тихие баги в скриптах: `"$DIR/$FILE"` при пустом `DIR` превращается в `/$FILE`, то есть в путь от корня. Чем это кончается для `rm`, разберём в подтеме про удаление.

## ls -l: что значит каждая колонка {#ls-long}

С картой разобрались, теперь научимся читать главный инструмент осмотра — длинный листинг. Каждую колонку `ls -l` нужно понимать точно: по ним определяют тип файла, права, владельца, ищут ответы на вопросы «почему не удаляется» и «кто съел место».

```text
$ cd /srv/app
$ ls -l
total 8
-rw-r--r--. 1 root  root  270 Oct 28 16:40 app.conf
lrwxrwxrwx. 1 root  root   11 Nov  2 09:31 current -> releases/v2
drwxr-xr-x. 2 alice alice  75 Nov  2 08:14 logs
drwxr-xr-x. 4 root  root   26 Nov  2 09:30 releases
-rwxr-xr-x. 1 root  root   42 Dec 15  2025 run.sh
```

Разберём строку `logs` по полям:

```text
d rwxr-xr-x . 2 alice alice 75 Nov  2 08:14 logs
│ │         │ │ │     │     │  │            │
│ │         │ │ │     │     │  │            имя
│ │         │ │ │     │     │  время (mtime)
│ │         │ │ │     │     размер в байтах
│ │         │ │ │     группа
│ │         │ │ владелец
│ │         │ число жёстких ссылок
│ │         SELinux-контекст или ACL
│ права: владелец, группа, остальные
тип
```

### Тип — первый символ

| Символ | Тип | Где встречается |
|---|---|---|
| `-` | обычный файл | конфиги, логи, программы |
| `d` | каталог | `/etc`, `logs` |
| `l` | символическая ссылка | `current -> releases/v2` |
| `c` | символьное устройство | `/dev/null`, терминалы |
| `b` | блочное устройство | диски: `/dev/sda`, `/dev/vda` |
| `p` | именованный канал (FIFO) | создаёт `mkfifo` |
| `s` | сокет | файлы сервисов в `/run` |

Последние четыре типа — «ненастоящие» файлы: данных на диске у них нет, это точки входа в ядро или в другой процесс. Вот как они выглядят:

```text
$ ls -l /dev/null /dev/vda /run/app.*
crw-rw-rw-. 1 root root   1, 3 Nov  2 19:05 /dev/null
brw-rw----. 1 root disk 252, 0 Nov  2 19:05 /dev/vda
prw-r--r--. 1 root root      0 Nov  2 19:31 /run/app.fifo
srwxr-xr-x. 1 root root      0 Nov  2 19:31 /run/app.sock
```

### Права — следующие девять символов

Три тройки `rwx`: для владельца (u), группы (g) и всех остальных (o). Дефис на месте буквы означает, что права нет. У файла `r` — читать, `w` — менять содержимое, `x` — запускать. У каталога смысл другой: `r` — видеть список имён, `w` — создавать и удалять в нём файлы, `x` — заходить внутрь и обращаться к файлам по имени. Вместо `x` иногда стоят `s`, `S`, `t` или `T` — это спецбиты (у `/tmp` права `drwxrwxrwt`). Подробно всё это — в главе «Права».

В нашем листинге `run.sh` имеет права `rwxr-xr-x`: владелец может всё, остальные читают и запускают. У `app.conf` — `rw-r--r--`: менять может только root.

### Точка или плюс после прав

Одиннадцатый символ говорит, есть ли у файла дополнительные механизмы доступа. По документации coreutils: `.` — есть SELinux-контекст и больше ничего, `+` — есть что-то ещё, обычно ACL. В RHEL с включённым SELinux точка стоит почти у всех файлов. Её нет, если у файла нет SELinux-метки, например в Docker-контейнере на хосте без SELinux.

Увидел `+` — значит, девять символов прав уже не вся правда, и нужно смотреть `getfacl`:

```text
$ setfacl -m u:bob:r app.conf
$ ls -l app.conf
-rw-r--r--+ 1 root root 270 Oct 28 16:40 app.conf
```

### Число ссылок

У файла это число его имён (жёстких ссылок), обычно 1. У каталога — 2 плюс число подкаталогов: у `releases` их два (`v1` и `v2`), поэтому стоит 4. Откуда берётся эта арифметика — в подтеме про inode.

### Владелец и группа

В inode хранятся не имена, а числа uid и gid. `ls` переводит их в имена через `/etc/passwd` и `/etc/group`. Если пользователя удалили, вместо имени останется число:

```text
$ ls -l /tmp/x
-rw-r--r--. 1 1005 root 0 Nov  2 19:07 /tmp/x
```

Такой файл после `userdel` остаётся «сиротой». Новый пользователь, которому достанется uid 1005, автоматически станет его владельцем. Числа вместо имён всегда показывает `ls -n`:

```text
$ ls -n
total 8
-rw-r--r--. 1    0    0 270 Oct 28 16:40 app.conf
lrwxrwxrwx. 1    0    0  11 Nov  2 09:31 current -> releases/v2
drwxr-xr-x. 2 1000 1000  75 Nov  2 08:14 logs
drwxr-xr-x. 4    0    0  26 Nov  2 09:30 releases
-rwxr-xr-x. 1    0    0  42 Dec 15  2025 run.sh
```

### Размер

Размер указан в байтах. Флаг `-h` переводит его в K, M, G (степени 1024):

```text
$ ls -lh logs
total 2.4M
-rw-r--r--. 1 alice alice 325K Nov  2 08:14 app.log
-rw-r--r--. 1 alice alice 2.0M Nov  1 23:59 app.log.1
-rw-r--r--. 1 alice alice  88K Oct 31 23:59 app.log.2.gz
-rw-r--r--. 1 alice alice 2.8K Nov  2 07:52 error.log
```

Три особых случая:

- **Символическая ссылка** — длина пути, записанного внутри. У `current` это 11 байт: ровно столько символов в `releases/v2`.
- **Каталог** — размер служебной таблицы имён, а не содержимого. На XFS маленький каталог хранит записи прямо в inode, поэтому у пустого каталога размер 6, а у `logs` — 75. На ext4 размер каталога кратен 4096: у `/backup` будет 4096. Сколько весит содержимое, показывает `du -sh` (о нём — в главе про диски).
- **Устройство** — вместо размера пара чисел `major, minor`: номер драйвера и номер устройства. У `/dev/null` это `1, 3`.

### Время

По умолчанию показан **mtime** — время последнего изменения содержимого (про остальные времена — отдельная подтема). Формат зависит от возраста. Если файл моложе полугода, видны дата и время (`Nov  2 08:14`). Если старше или если время в будущем, вместо часов стоит год (`Dec 15  2025`). Полную метку даёт `--full-time`, а `--time-style=long-iso` — короткий ISO-формат:

```text
$ ls -l --full-time run.sh
-rwxr-xr-x. 1 root root 42 2025-12-15 11:03:00.000000000 +0000 run.sh
$ ls -l --time-style=long-iso run.sh
-rwxr-xr-x. 1 root root 42 2025-12-15 11:03 run.sh
```

### Имя

У ссылки после имени стоит стрелка и цель: `current -> releases/v2`. Имена с пробелами и спецсимволами `ls` в терминале берёт в кавычки (`'my file'`) и сдвигает остальные имена на пробел, чтобы колонки не поехали. Если вывод уходит в пайп или файл, кавычек нет. Подробнее — в подтеме про создание файлов.

### Строка total

Это не число файлов и не сумма их размеров. `total` показывает, сколько места **на диске** занимают перечисленные файлы, в блоках по 1 КиБ. В `/srv/app` это 8: `app.conf` (270 байт) и `run.sh` (42 байта) занимают по целому блоку в 4 КиБ, а ссылка и каталоги на XFS хранятся в самом inode и блоков не занимают. Это видно по колонке `-s`:

```text
$ ls -ls
total 8
4 -rw-r--r--. 1 root  root  270 Oct 28 16:40 app.conf
0 lrwxrwxrwx. 1 root  root   11 Nov  2 09:31 current -> releases/v2
0 drwxr-xr-x. 2 alice alice  75 Nov  2 08:14 logs
0 drwxr-xr-x. 4 root  root   26 Nov  2 09:30 releases
4 -rwxr-xr-x. 1 root  root   42 Dec 15  2025 run.sh
```

> **Ловушка.** Если `ls -l` указать символическую ссылку на каталог, он покажет саму ссылку, а не содержимое: `ls -l /bin` выведет одну строку `/bin -> usr/bin`. Содержимое покажут `ls -l /bin/` (со слэшем на конце) или `ls -lL /bin`. Без `-l`, `-d` и `-F` ссылка из командной строки разыменовывается сама: `ls /bin` покажет программы.

> **На практике.** В RHEL есть готовые алиасы из `/etc/profile.d/colorls.sh`: `ll` — это `ls -l --color=auto`, а `l.` — это `ls -d .* --color=auto`, то есть скрытые файлы текущего каталога.

## ls: показать нужное и отсортировать {#ls}

Листинг мы читать умеем. Теперь научимся заставлять `ls` показывать именно то, что нужно: скрытые файлы, сам каталог вместо содержимого, самые свежие или самые большие файлы, нужное время.

### Скрытые файлы: -a и -A

Скрытый файл — это просто имя, которое начинается с точки. Никакого атрибута «скрытый» нет: `ls` пропускает такие имена по соглашению. Скрытыми обычно делают конфиги: `.bashrc`, `.ssh` в домашнем каталоге, `.env` у нашего приложения.

```text
$ ls
app.conf  current  logs  releases  run.sh
$ ls -a
.  ..  app.conf  current  .env  logs  releases  run.sh
$ ls -A
app.conf  current  .env  logs  releases  run.sh
```

`-a` (all) показывает всё, включая `.` и `..`. `-A` (almost all) — всё, кроме них. В скриптах и при подсчёте файлов нужен `-A`: `.` и `..` есть в любом каталоге и только мешают.

Заметь, что `.env` стоит между `current` и `logs`. Сортировка в локали `en_US.UTF-8` не учитывает точку в начале и регистр букв. В локали `C` (`LANG=C ls -a`) скрытые файлы окажутся в начале, а заглавные буквы — раньше строчных.

### Сам каталог: -d

`ls каталог` показывает содержимое. Чтобы увидеть сам каталог — его права, владельца, время, — нужен `-d`:

```text
$ ls -ld logs
drwxr-xr-x. 2 alice alice 75 Nov  2 08:14 logs
```

Это первое, что делают при ошибке «Permission denied» на создание файла: смотрят права каталога, а не файлов в нём. Вместе с шаблоном `-d` даёт полезные трюки:

```text
$ ls -d */
current/  logs/  releases/
$ ls -d .*
.  ..  .env
```

`ls -d */` выводит только подкаталоги: шаблон `*/` совпадает лишь с каталогами. Только с каталогами — и со ссылками на них, поэтому в список попал `current/`. `ls -d .*` показывает скрытые имена текущего каталога (именно это делает алиас `l.`).

### Сортировка: -t, -S, -r

По умолчанию `ls` сортирует по имени. `-t` сортирует по времени (свежие сверху), `-S` — по размеру (большие сверху), `-r` переворачивает любую сортировку.

```text
$ cd /srv/app/logs
$ ls -lt
total 2400
-rw-r--r--. 1 alice alice  331992 Nov  2 08:14 app.log
-rw-r--r--. 1 alice alice    2837 Nov  2 07:52 error.log
-rw-r--r--. 1 alice alice 2026316 Nov  1 23:59 app.log.1
-rw-r--r--. 1 alice alice   90000 Oct 31 23:59 app.log.2.gz
$ ls -ltr
total 2400
-rw-r--r--. 1 alice alice   90000 Oct 31 23:59 app.log.2.gz
-rw-r--r--. 1 alice alice 2026316 Nov  1 23:59 app.log.1
-rw-r--r--. 1 alice alice    2837 Nov  2 07:52 error.log
-rw-r--r--. 1 alice alice  331992 Nov  2 08:14 app.log
$ ls -lS
total 2400
-rw-r--r--. 1 alice alice 2026316 Nov  1 23:59 app.log.1
-rw-r--r--. 1 alice alice  331992 Nov  2 08:14 app.log
-rw-r--r--. 1 alice alice   90000 Oct 31 23:59 app.log.2.gz
-rw-r--r--. 1 alice alice    2837 Nov  2 07:52 error.log
```

`ls -ltr` — любимая команда для логов: самые свежие файлы оказываются внизу, у самого приглашения, и не уезжают за экран. Нужно одно имя — отрежь его через `head`:

```text
$ ls -t | head -1
app.log
```

Это работает, потому что в пайп `ls` выводит по одному имени в строке (ниже подробнее). Сортировка `-t` идёт по точному времени с наносекундами, а не по минутам, которые видно на экране.

> **Ловушка.** `-S` сортирует файлы одного каталога по их собственному размеру. Каталоги тоже участвуют, но со своими крошечными размерами таблиц имён, а не содержимого. Найти, какой подкаталог съел место, `ls -S` не поможет — для этого есть `du` (глава про диски).

### Номера по порядку: -v

Ротированные логи с номерами `ls` сортирует как строки, и `10` оказывается раньше `2`. `-v` сравнивает числа внутри имён как числа:

```text
$ ls
app.log  app.log.1  app.log.10  app.log.11  app.log.2
$ ls -v
app.log  app.log.1  app.log.2  app.log.10  app.log.11
```

### Какое время: -u, -c, --time=birth

`ls -l` показывает mtime. `-u` подставляет atime (время последнего чтения), `-c` — ctime (время изменения inode), `--time=birth` — время создания. Что означает каждое время, разберём в отдельной подтеме, а здесь — ловушка с сортировкой. Возьмём каталог с тремя файлами:

```text
$ ls -lu
total 0
-rw-r--r--. 1 root root 0 Nov  2 12:00 alpha.log
-rw-r--r--. 1 root root 0 Nov  2 08:00 beta.log
-rw-r--r--. 1 root root 0 Nov  2 11:00 gamma.log
$ ls -ltu
total 0
-rw-r--r--. 1 root root 0 Nov  2 12:00 alpha.log
-rw-r--r--. 1 root root 0 Nov  2 11:00 gamma.log
-rw-r--r--. 1 root root 0 Nov  2 08:00 beta.log
$ ls -u
alpha.log  gamma.log  beta.log
```

`ls -lu` **показывает** atime, но сортирует по имени. Чтобы ещё и сортировать по atime, нужен `ls -ltu`. А без `-l` ключ `-u` сам включает сортировку по atime. С `-c` правила те же. Это не баг, так написано в `ls --help`: «with -lt: sort by, and show, access time; with -l: show access time and sort by name; otherwise: sort by access time, newest first».

### Номер inode: -i

```text
$ cd /srv/app
$ ls -i
262283 app.conf  262278 current  262274 logs  655488 releases  262277 run.sh
```

Числа слева — номера inode. Что это такое и почему это самая важная колонка главы, разберём в следующей подтеме.

### Рекурсия: -R

`-R` обходит подкаталоги и выводит содержимое каждого с заголовком:

```text
$ ls -R releases
releases:
v1  v2

releases/v1:
bin  conf

releases/v1/bin:

releases/v1/conf:

releases/v2:
bin  conf

releases/v2/bin:

releases/v2/conf:
```

Небольшое дерево так удобно окинуть взглядом. Для поиска и обработки файлов в глубину есть `find` — у него фильтры по имени, времени и размеру (глава «Поиск»).

### Значки типа: -F

`-F` добавляет к имени значок типа:

```text
$ ls -F
app.conf  current@  logs/  releases/  run.sh*
```

- `/` — каталог;
- `*` — исполняемый файл;
- `@` — символическая ссылка;
- `|` — именованный канал;
- `=` — сокет.

Это спасает в терминале без цветов и в выводе, вставленном в тикет.

### Колонки или столбик: -1 и пайпы

В терминале `ls` раскладывает имена по колонкам под ширину экрана. Если вывод уходит в пайп или файл, `ls` пишет по одному имени в строке, без колонок и без кавычек:

```text
$ ls | cat
app.conf
current
logs
releases
run.sh
$ ls logs | wc -l
4
```

Поэтому `ls | head -1` и `ls | wc -l` работают как ожидаешь. `-1` включает столбик и в терминале, `-C` — наоборот, колонки в пайпе. Разбирать вывод `ls` в скриптах всё равно не стоит: имя с переводом строки сломает подсчёт (это разобрано в последней подтеме).

### SELinux-контекст: -Z

`-Z` показывает SELinux-контекст, который в `ls -l` спрятан за точкой:

```text
$ ls -Z app.conf
unconfined_u:object_r:var_t:s0 app.conf
```

Зачем он нужен и как его чинить — в главе про SELinux. Здесь главное: точка в `ls -l` значит, что контекст есть, а какой — показывает `-Z`.

### Сводка флагов

| Флаг | Что делает |
|---|---|
| `-l` | длинный формат |
| `-a` / `-A` | со скрытыми; `-A` — без `.` и `..` |
| `-d` | сам каталог, а не содержимое |
| `-h` | размеры в K, M, G |
| `-t` / `-S` | по времени / по размеру, сверху большие и свежие |
| `-r` | перевернуть сортировку |
| `-v` | числа в именах по порядку |
| `-u` / `-c` | atime / ctime; сортирует только с `-t` или без `-l` |
| `--time=birth` | время создания |
| `--full-time` | полная метка времени |
| `-i` | номер inode |
| `-n` | uid и gid числами |
| `-s` | занятые блоки по 1 КиБ |
| `-R` | рекурсивно |
| `-F` | значки типа |
| `-1` | по одному в строке |
| `-L` | показывать цель ссылки, а не ссылку |
| `-Z` | SELinux-контекст |

## Inode: имя отдельно, файл отдельно {#inode}

`ls -i` показал числа слева от имён. Это номера inode, и они объясняют почти всё странное в этой главе: почему `mv` гигабайтного файла мгновенный, почему после `rm` не освобождается место, почему у каталога четыре ссылки.

### Что такое inode

Файловая система хранит файл в двух частях.

- **Inode** — служебная запись фиксированного размера. В ней тип файла, права, владелец (uid и gid), размер, времена, число ссылок и адреса блоков с данными.
- **Блоки данных** — само содержимое.

Одного в inode нет — **имени**. Имя хранится в каталоге.

### Каталог — это таблица «имя → inode»

Каталог — особый файл, внутри которого список пар «имя — номер inode». `ls` просто читает эту таблицу. Посмотрим на номера вместе с `.` и `..`:

```text
$ ls -lia
total 12
262272 drwxr-xr-x. 4 root  root   91 Nov  2 09:31 .
   128 drwxr-xr-x. 6 root  root   51 Nov  2 19:29 ..
262283 -rw-r--r--. 1 root  root  270 Oct 28 16:40 app.conf
262278 lrwxrwxrwx. 1 root  root   11 Nov  2 09:31 current -> releases/v2
262276 -rw-------. 1 root  root   15 Oct 30 10:00 .env
262274 drwxr-xr-x. 2 alice alice  75 Nov  2 08:14 logs
655488 drwxr-xr-x. 4 root  root   26 Nov  2 09:30 releases
262277 -rwxr-xr-x. 1 root  root   42 Dec 15  2025 run.sh
$ ls -di /srv/app /srv
   128 /srv  262272 /srv/app
```

Запись `.` указывает на inode 262272 — это сам `/srv/app`. Запись `..` указывает на 128 — это `/srv`. Никакой магии: `.` и `..` — обычные строки таблицы, которые ведут на соседние inode.

Отсюда и число ссылок у каталога. На `releases` ведут три вида записей: имя `releases` в `/srv/app`, его собственная `.` и запись `..` в каждом из двух подкаталогов. Итого 1 + 1 + 2 = 4. У пустого каталога ссылок 2: имя у родителя и своя `.`.

```text
$ ls -lid releases releases/v1/..
655488 drwxr-xr-x. 4 root root 26 Nov  2 09:30 releases
655488 drwxr-xr-x. 4 root root 26 Nov  2 09:30 releases/v1/..
```

Из того, что имя хранится отдельно от файла, следует почти вся остальная глава:

- **Переименование** в пределах одной ФС меняет только строку в таблице. Поэтому оно мгновенное при любом размере файла, а номер inode остаётся прежним (подтема про mv).
- **Жёсткая ссылка** — вторая строка таблицы с тем же номером inode (подтема про ссылки).
- **Удаление** убирает строку из таблицы. Сам inode и данные освобождаются, только когда строк не осталось и файл никто не держит открытым (подтема про rm и последняя подтема).
- **Права на каталог** — это права на таблицу имён. Поэтому удалить файл можно без прав на сам файл, но не без прав на каталог.
- Номер inode уникален только **внутри одной ФС**. Поэтому жёсткие ссылки и переименование между ФС невозможны.

### stat: inode целиком

`ls -l` показывает выборку из inode, а `stat` — всё:

```text
$ stat app.conf
  File: app.conf
  Size: 270             Blocks: 8          IO Block: 4096   regular file
Device: 700h/1792d      Inode: 262283      Links: 1
Access: (0644/-rw-r--r--)  Uid: (    0/    root)   Gid: (    0/    root)
Context: unconfined_u:object_r:var_t:s0
Access: 2026-10-28 16:40:00.000000000 +0000
Modify: 2026-10-28 16:40:00.000000000 +0000
Change: 2026-11-02 19:32:31.416558857 +0000
 Birth: 2026-11-02 19:28:40.340564142 +0000
```

Разберём по строкам:

- `Size` — размер в байтах. `Blocks` — сколько занято на диске, **в единицах по 512 байт**: 8 × 512 = 4 КиБ. Файл в 270 байт всё равно занимает целый блок ФС. `IO Block` — размер блока для ввода-вывода. В конце строки — тип файла словами.
- `Device` — номер устройства, на котором лежит ФС (в шестнадцатеричном и десятичном виде). Дальше номер inode и число ссылок.
- `Access: (0644/-rw-r--r--)` — права числом и буквами, за ними uid и gid вместе с именами.
- `Context` — SELinux-контекст. Строка появляется, только если SELinux включён.
- Четыре времени — Access, Modify, Change и Birth. Им посвящена отдельная подтема.

Для скриптов есть `stat -c` с форматом:

```text
$ stat -c '%i %h %s %U %a %n' run.sh logs
262277 1 42 root 755 run.sh
262274 2 75 alice 755 logs
```

| Код | Что выводит |
|---|---|
| `%n` | имя |
| `%s` | размер в байтах |
| `%b` | занятые блоки по 512 байт |
| `%i` | номер inode |
| `%h` | число жёстких ссылок |
| `%U` / `%u` | владелец: имя / uid |
| `%G` / `%g` | группа: имя / gid |
| `%a` / `%A` | права числом / буквами |
| `%F` | тип файла словами |
| `%x` `%y` `%z` `%w` | atime, mtime, ctime, birth |
| `%X` `%Y` `%Z` `%W` | те же времена в секундах с 1970 года |

На ссылку `stat` по умолчанию показывает её саму (`symbolic link`). `stat -L` идёт к цели:

```text
$ stat -c %F current
symbolic link
$ stat -L -c %F current
directory
```

### Inode не бесконечны

Inode тоже занимают место на диске, и их число ограничено. Сколько занято и сколько осталось, показывает `df -i`:

```text
$ df -i /srv
Filesystem     Inodes IUsed  IFree IUse% Mounted on
/dev/loop0     153600    26 153574    1% /srv
```

XFS выделяет inode по мере надобности, а у ext4 их число задаётся при создании ФС раз и навсегда. Как выглядит сервер, у которого inode кончились, а место есть, — в последней подтеме.

### file: тип по содержимому

Linux не смотрит на расширение: `.txt`, `.conf`, `.sh` — просто часть имени. Чтобы файл запустился, нужны бит `x` и подходящее содержимое (строка `#!` в начале или ELF-заголовок). Что лежит внутри на самом деле, определяет `file`: он сверяет первые байты с базой сигнатур.

```text
$ file app.conf run.sh site.conf empty blob.bin
app.conf:  ASCII text
run.sh:    Bourne-Again shell script, ASCII text executable
site.conf: ASCII text, with CRLF line terminators
empty:     empty
blob.bin:  data
$ file backup.txt | cut -d, -f1
backup.txt: gzip compressed data
$ file /usr/bin/bash | cut -d, -f1-2
/usr/bin/bash: ELF 64-bit LSB pie executable, x86-64
```

`backup.txt` на самом деле — gzip-архив, расширение врёт. У `site.conf` строки заканчиваются по-виндовому (CRLF), и такой конфиг или скрипт может вести себя странно (подробнее — в подтеме про чтение файлов). `data` означает, что тип распознать не удалось. Ссылку `file` описывает словами, а с `-L` смотрит на цель; `-i` выдаёт MIME-тип:

```text
$ file /srv/app/current /dev/null
/srv/app/current: symbolic link to releases/v2
/dev/null:        character special (1/3)
$ file -i app.conf
app.conf: text/plain; charset=us-ascii
```

## Создание файлов и каталогов, имена с подвохом {#create}

Теперь мы знаем, что файл — это inode плюс строка в каталоге. Создать файл — значит выделить inode и вписать имя в таблицу. Посмотрим, какими способами это делают и где подстерегают неприятности.

### touch: пустой файл или новое время

`touch` создаёт пустой файл, если его нет. Если файл уже есть, содержимое остаётся прежним, а atime и mtime становятся «сейчас»:

```text
$ touch notes.txt
$ ls -l notes.txt
-rw-r--r--. 1 root root 0 Nov  2 19:40 notes.txt
```

Флаг `-c` запрещает создавать: «обнови время, если файл есть, а если нет — ничего не делай». Остальные флаги `touch` (`-d`, `-r`, `-a`, `-m`) относятся ко времени, они разобраны в подтеме про три времени.

### Перенаправление: > и >>

`>` создаёт файл, а если он уже есть — **обрезает до нуля** и пишет заново. `>>` дописывает в конец. Отличие в один символ, и одна опечатка в `> /etc/app.conf` стоит конфига.

Защита от этого — `noclobber`: с ним `>` отказывается перезаписывать существующий файл, а `>|` перезаписывает явно.

```text
$ set -o noclobber
$ echo x > report.txt
bash: report.txt: cannot overwrite existing file
$ echo x >| report.txt
```

Чтобы опустошить файл, не удаляя его, пишут `: > file` (`:` — пустая команда, которая ничего не выводит) или `truncate -s 0 file`. Это важно для логов: inode остаётся тем же, и процесс, который пишет в файл, продолжает писать в него же. Почему `rm` вместо этого — плохая идея, разберём в последней подтеме.

### mkdir: -p, -m, -v

Без флагов `mkdir` создаёт один уровень и ругается, если родителя нет или каталог уже есть:

```text
$ mkdir conf/nginx
mkdir: cannot create directory ‘conf/nginx’: No such file or directory
$ mkdir -p conf/nginx
$ mkdir conf
mkdir: cannot create directory ‘conf’: File exists
$ mkdir -p conf
$ echo $?
0
```

`-p` (parents) создаёт всю цепочку и молчит, если каталог уже существует. Поэтому в скриптах пишут `mkdir -p`: повторный запуск не падает. `-v` рассказывает, что создано:

```text
$ mkdir -pv a/b/c
mkdir: created directory 'a'
mkdir: created directory 'a/b'
mkdir: created directory 'a/b/c'
```

`-m` задаёт права сразу и точно, без учёта umask. Но только последнему каталогу в цепочке: промежуточные, созданные через `-p`, получают обычные права.

```text
$ mkdir -p -m 700 x/y/z
$ ls -ld x x/y x/y/z
drwxr-xr-x. 3 root root 15 Nov  2 19:09 x
drwxr-xr-x. 3 root root 15 Nov  2 19:09 x/y
drwx------. 2 root root  6 Nov  2 19:09 x/y/z
```

### Имена: регистр и расширения

Имена чувствительны к регистру: `Notes.txt` и `notes.txt` — два разных файла, и оба спокойно живут в одном каталоге. Расширение — просто часть имени, система на него не смотрит (тип определяет содержимое, см. `file` в подтеме про inode).

### Пробелы и кавычки

bash делит командную строку на слова по пробелам. Поэтому `touch my file` создаёт **два** файла: `my` и `file`. Чтобы пробел стал частью имени, его экранируют — тремя способами:

```text
$ touch "my file"
$ touch 'my file'
$ touch my\ file
```

Двойные и одинарные кавычки отличаются тем, что в двойных bash подставляет переменные (`"$HOME"`), а в одинарных нет. От пробелов защищают и те, и другие.

Больнее всего пробелы бьют в переменных. Без кавычек bash снова делит значение на слова:

```text
$ touch my file
$ touch "my file"
$ f="my file"
$ ls -l $f
-rw-r--r--. 1 root root 0 Nov  2 19:29 file
-rw-r--r--. 1 root root 0 Nov  2 19:29 my
$ ls -l "$f"
-rw-r--r--. 1 root root 0 Nov  2 19:29 'my file'
```

`ls -l $f` показал совсем другие файлы. С `rm $f` вместо одного файла удалились бы два чужих. Правило для скриптов: переменную с путём всегда пиши в кавычках — `"$f"`.

Как такие имена показывает `ls`, зависит от того, куда идёт вывод. В терминале имя берётся в кавычки, а остальные сдвигаются на пробел, чтобы колонки не поехали. В пайпе имена выводятся как есть:

```text
$ ls -l
total 0
-rw-r--r--. 1 root root 0 Nov  2 19:29  file
-rw-r--r--. 1 root root 0 Nov  2 19:29  my
-rw-r--r--. 1 root root 0 Nov  2 19:29 'my file'
$ ls | cat
file
my
my file
```

Кавычки в выводе `ls` — это готовый синтаксис bash: имя можно скопировать прямо в команду. Отключает их `ls -N`.

### Имя, которое начинается с дефиса

Имя `-rf` разрешено, но любая команда примет его за ключи:

```text
$ touch -rf
touch: failed to get attributes of 'f': No such file or directory
$ touch -- -rf
$ touch ./-rf
```

`touch` понял `-rf` как `-r f` («возьми время у файла f»). `--` означает «ключи кончились, дальше только имена», а `./-rf` просто не начинается с дефиса. Те же два приёма нужны, чтобы такой файл удалить, — об этом в подтеме про rm.

> **Ловушка.** Кавычки от дефиса не спасают: `touch '-rf'` — то же самое, что `touch -rf`. Кавычки снимает bash ещё до запуска, и команда всё равно получает строку `-rf`. Кавычки защищают от bash (пробелы, `*`, `$`), а от разбора ключей защищают только `--` и `./`.

## Чтение файлов: cat, less, head, tail, wc {#view}

Файлы созданы. Прежде чем копировать и удалять, научимся быстро заглядывать внутрь: целиком, постранично, с начала, с конца и «в реальном времени». И видеть то, чего на экране не видно.

### cat и невидимые символы

`cat` выводит файл целиком. `-n` нумерует строки, а `-A` показывает невидимое: табуляцию как `^I`, конец строки как `$`, возврат каретки как `^M`. В `current/conf` лежит конфиг `site.conf`, который пришёл с Windows-машины:

```text
$ cd /srv/app/current/conf
$ cat site.conf
server {
	listen 80;
}
$ cat -A site.conf
server {^M$
^Ilisten 80;^M$
}^M$
```

На экране всё чисто, а в конце каждой строки сидит `\r` (CRLF вместо LF). Скрипт с такими строками не запустится, и ошибка выглядит загадочно:

```text
$ ./w.sh
bash: ./w.sh: /bin/bash^M: bad interpreter: No such file or directory
```

Система ищет интерпретатор `/bin/bash\r`, а такого нет. Лечится удалением `\r`: `sed -i 's/\r$//' w.sh` (или утилитой `dos2unix`, если она установлена). `file` предупредит заранее: `with CRLF line terminators`.

Второй невидимый подвох — **нет перевода строки в конце файла**. Рядом лежит `env`:

```text
$ cat env
PORT=8080 
HOST=0.0.0.0
DEBUG=false[root@server1 conf]#
```

Приглашение прилипло к последней строке: после `false` нет `\n`. Посмотрим внимательнее (`echo` в конце только переводит строку, чтобы приглашение не прилипало снова):

```text
$ cat -A env; echo
PORT=8080 $
HOST=0.0.0.0$
DEBUG=false
$ wc -l env
2 env
```

`wc -l` насчитал 2 строки вместо 3: он считает символы перевода строки, а не строки. Заодно `-A` показал пробел после `8080`. Из-за такого хвостового пробела значение `PORT` может не распознаться.

> **Ловушка.** `cat` бинарного файла выводит мусор, который терминал может принять за управляющие последовательности, и дальше вместо букв пойдут каракули. Лечится командой `reset`. Не знаешь, что в файле, — сначала `file`.

### less: постранично

Длинные файлы читают в `less`: он не грузит файл целиком и открывает многогигабайтный лог мгновенно. Основные клавиши (по `man less`):

| Клавиша | Что делает |
|---|---|
| `Space` / `b` | страница вперёд / назад |
| `g` / `G` | в начало / в конец |
| `/текст` | искать вперёд |
| `?текст` | искать назад |
| `n` / `N` | следующее / предыдущее совпадение |
| `F` | следить за ростом файла, как `tail -f`; выход — `Ctrl+C` |
| `q` | выйти |

Полезные ключи запуска: `less -N` нумерует строки, `less -S` не переносит длинные строки (удобно для широких логов), `less +F` сразу включает слежение.

### head и tail: начало и конец

`head` показывает первые 10 строк, `tail` — последние 10. Число задаёт `-n`. Для примеров возьмём файл `ten.txt` из десяти строк, от `line 1` до `line 10`:

```text
$ head -n 3 ten.txt
line 1
line 2
line 3
$ tail -n 2 ten.txt
line 9
line 10
```

`head -3` — старая короткая форма того же `-n 3`. Интереснее знаки перед числом:

```text
$ head -n -7 ten.txt
line 1
line 2
line 3
$ tail -n +9 ten.txt
line 9
line 10
```

`head -n -7` выводит всё, **кроме** последних 7 строк. `tail -n +9` выводит всё, **начиная** с 9-й строки. Самый частый случай — `tail -n +2`, чтобы отрезать строку заголовка у CSV или у вывода `ps`. `-c` считает байты вместо строк: `head -c 12`. Если файлов несколько, каждый получает заголовок:

```text
$ head -n 2 ten.txt app.log
==> ten.txt <==
line 1
line 2

==> app.log <==
new line 1
new line 2
```

Нужна одна строка из середины — `sed -n 5p ten.txt` или `head -n 5 ten.txt | tail -n 1`.

### tail -f и tail -F: следить за логом

`tail -f` выводит новые строки по мере того, как их дописывают. Но держится он за **открытый файл**, то есть за inode, а не за имя. В ночь ротации logrotate переименовывает `app.log` в `app.log.1` и создаёт новый `app.log`. `tail -f` продолжает смотреть в старый файл, который теперь называется `app.log.1`. Новые записи идут в новый файл, а на экране тишина.

Проверим. Пока работал `tail -f b.log`, файл переименовали в `b.log.1` и создали новый `b.log` со строкой `after rotate`. Потом в старый файл, уже `b.log.1`, дописали `to old`:

```text
$ tail -f b.log
line 1
line 2
line 3
to old
```

`after rotate` так и не появилась, зато пришла строка, дописанная в старый файл.

`tail -F` следит за **именем**: заметив, что файл под этим именем пропал, а потом появился новый, он открывает его заново и пишет об этом:

```text
$ tail -F app.log
line 1
line 2
line 3
line 4
tail: 'app.log' has become inaccessible: No such file or directory
tail: 'app.log' has appeared;  following new file
new line 1
new line 2
```

Если новый файл появляется раньше, чем `tail` успевает заметить пропажу (так бывает, когда `tail` опрашивает файл по таймеру, а не получает события inotify), вместо этой пары будет одна строка: `tail: 'app.log' has been replaced;  following new file`.

> **На практике.** Логи, которые ротируются, смотри через `tail -F`, иначе после полуночи будешь ждать строк, которые давно пишутся в другой файл. `less +F` ведёт себя как `tail -f`, то есть тоже держится за открытый файл.

### wc: строки, слова, байты

```text
$ wc env
 2  3 35 env
$ wc -l site.conf env
 3 site.conf
 2 env
 5 total
$ wc -l < /etc/passwd
17
```

Без флагов `wc` выводит строки, слова и байты. `-l` — только строки, `-w` — слова, `-c` — байты, `-m` — символы (в UTF-8 буква кириллицы — 2 байта, но 1 символ). Если подать файл через `<`, `wc` не знает имени и выводит одно число. Это удобно в скриптах: `n=$(wc -l < file)`.

## Шаблоны: * ? [ ] и { } {#glob}

До сих пор мы работали с файлами поштучно. Но работа на сервере — это пачки: все логи за октябрь, все `.tmp`, все конфиги, кроме одного. Для этого есть шаблоны (glob). Главное, что о них нужно знать: шаблон раскрывает **bash**, а не команда.

### Кто раскрывает шаблон

Перед запуском команды bash заменяет шаблон списком подходящих имён, отсортированных по алфавиту. Команда получает уже готовый список: `rm *.log` превращается в `rm access.log app.log error.log`, и `rm` звёздочки никогда не видит. Отсюда правило: прежде чем выполнить опасную команду с шаблоном, подставь вместо неё `echo` и посмотри, во что шаблон раскроется.

За ночь в `logs` прибавилось файлов:

```text
$ cd /srv/app/logs
$ ls -A
access.log  app.log.1     error.log    .rotate.state
app.log     app.log.2.gz  error.log.1
$ echo *
access.log app.log app.log.1 app.log.2.gz error.log error.log.1
$ echo *.log
access.log app.log error.log
$ echo app.log.?
app.log.1
$ echo *.[0-9]
app.log.1 error.log.1
$ echo *.log.*
app.log.1 app.log.2.gz error.log.1
$ echo [!a]*
error.log error.log.1
```

| Шаблон | Совпадает с |
|---|---|
| `*` | любой строкой, в том числе пустой |
| `?` | ровно одним любым символом |
| `[abc]` | одним символом из списка |
| `[a-z]`, `[0-9]` | одним символом из диапазона |
| `[!abc]` или `[^abc]` | одним символом не из списка |
| `[[:digit:]]`, `[[:upper:]]` | одним символом из класса |

Шаблон сравнивается с именем **целиком**: `*.log` не совпадает с `app.log.1`, потому что после `.log` есть ещё `.1`. А `*` не пересекает `/`: `*/*.conf` — это файлы `.conf` ровно на один уровень ниже.

### Скрытые файлы и .*

`*` не совпадает с именами, которые начинаются с точки: в `echo *` выше нет `.rotate.state`. Хочется написать `.*`, но в bash 5.1 (он в RHEL 9) этот шаблон совпадает ещё и с `.` и `..`:

```text
$ echo .*
. .. .rotate.state
$ echo .[!.]*
.rotate.state
```

> **Ловушка.** `chown -R alice .*` в `/home/alice` уйдёт через `..` в `/home` и сменит владельца у всех домашних каталогов. `rm` от этого защищён (`refusing to remove '.' or '..'`), а `chown` и `chmod` — нет. Безопасные варианты: `.[!.]*` (скрытые, кроме `.` и `..`), `.??*` (скрытые длиной от трёх символов) или опция `dotglob`, о ней ниже. В bash 5.2 это поведение уже отключено по умолчанию (опция `globskipdots`), но в RHEL 9 стоит 5.1.

С `shopt -s dotglob` звёздочка начинает брать и скрытые файлы, но не `.` и `..`:

```text
$ shopt -s dotglob
$ echo *
access.log app.log app.log.1 app.log.2.gz error.log error.log.1 .rotate.state
$ shopt -u dotglob
```

### Если совпадений нет

Если ни одно имя не подошло, bash оставляет шаблон как есть, и команда получает буквальную строку `*.txt`:

```text
$ echo *.txt
*.txt
$ ls *.txt
ls: cannot access '*.txt': No such file or directory
```

В скрипте это ломает циклы: `for f in *.txt` при отсутствии файлов выполнится один раз, с `f='*.txt'`. Поведение меняют две опции:

- `shopt -s nullglob` — шаблон без совпадений исчезает. Цикл не выполнится ни разу, но `ls *.txt` превратится в просто `ls` и покажет **весь** каталог. С `rm` такое опасно.
- `shopt -s failglob` — шаблон без совпадений считается ошибкой, и команда не запускается:

```text
$ shopt -s failglob
$ ls *.txt
bash: no match: *.txt
```

### Кавычки выключают шаблоны

В кавычках (`"*.log"`, `'*.log'`) или с обратным слэшем (`\*.log`) звёздочка — просто символ. Так шаблон передают программам, которые сравнивают имена сами, например `find -name`. Забытые кавычки дают три разных результата в зависимости от того, где ты стоишь:

```text
$ cd /srv/app/logs
$ find . -name *.log
find: paths must precede expression: `app.log'
find: possible unquoted pattern after predicate `-name'?
$ cd /srv/app/current
$ ls
bin  conf  install.log
$ find /srv/app -name *.log
/srv/app/releases/v2/install.log
$ find /srv/app -name "*.log"
/srv/app/releases/v2/install.log
/srv/app/logs/app.log
/srv/app/logs/error.log
/srv/app/logs/access.log
```

В `logs` шаблон раскрылся в три имени, и `find` выдал ошибку. В `current` совпадение нашлось ровно одно, и `find` **молча** искал только `install.log` — без ошибки, но с неправильным ответом. А там, где совпадений нет вовсе, шаблон дойдёт до `find` целым, и команда «случайно» сработает. Поэтому шаблон для `find` всегда пишут в кавычках.

### Шаблон — не регулярное выражение

Значки похожи, но смысл у них разный:

| Задача | Шаблон (glob) | Регулярное выражение |
|---|---|---|
| любая строка | `*` | `.*` |
| один любой символ | `?` | `.` |
| символ не из списка | `[!abc]` | `[^abc]` |
| буквальная точка | `.` | `\.` |
| привязка к началу и концу | всегда ко всему имени | нужно писать `^` и `$` |

Шаблоны понимают bash, `find -name`, `case` в скриптах, `.gitignore`. Регулярные выражения — `grep`, `sed`, `awk`, `find -regex`.

Частая ошибка — перенести шаблон в `grep`. В регулярном выражении `*` означает «повторить предыдущий символ сколько угодно раз», а `.` — «любой символ». Звёздочке в самом начале выражения повторять нечего, и `grep` в базовом синтаксисе считает её обычным символом. Для опыта положим в `logs` файл с именем `*xlog`:

```text
$ ls | grep '*.log'
*xlog
$ ls | grep '\.log$'
access.log
app.log
error.log
```

`grep '*.log'` искал буквальную звёздочку, за ней любой символ и `log`. Нашёлся только `*xlog`, а настоящие логи — нет. С `grep -E` ведущая звёздочка просто игнорируется, и выражение превращается в `.log`: под него попадёт и `xlog`. Нужное выражение — `\.log$`: буквальная точка, `log` и конец строки.

### Расширенные шаблоны: extglob

С `shopt -s extglob` появляются шаблоны с условиями. Самый полезный — «всё, кроме»:

```text
$ shopt -s extglob
$ echo !(*.log)
app.log.1 app.log.2.gz error.log.1
$ echo *.@(gz|1)
app.log.1 app.log.2.gz error.log.1
```

`!(шаблон)` — всё, что не совпадает; `@(a|b)` — ровно одно из; `?(…)`, `*(…)`, `+(…)` — ноль или один раз, сколько угодно, один и больше раз. `rm -- !(*.conf)` удалит в каталоге всё, кроме конфигов.

> **Ловушка.** По умолчанию `extglob` выключен. В интерактивном bash его часто включает пакет bash-completion (`shopt -s extglob progcomp` в его скрипте), поэтому в терминале всё работает. А тот же код в скрипте или в cron падает с синтаксической ошибкой, когда bash доходит до этой строки, причём всё, что выше, уже выполнено. В скрипте пиши `shopt -s extglob` отдельной строкой до первого такого шаблона.

```text
$ bash cleanup.sh
cleanup.sh: line 3: syntax error near unexpected token `('
cleanup.sh: line 3: `rm -- !(*.conf)'
```

### Фигурные скобки — не шаблон

`{…}` похожи на шаблоны, но устроены иначе: они не смотрят в ФС, а просто **генерируют строки**:

```text
$ echo {a,b,c}.conf
a.conf b.conf c.conf
$ echo {1..5}
1 2 3 4 5
$ echo {01..12}
01 02 03 04 05 06 07 08 09 10 11 12
$ echo {0..20..5}
0 5 10 15 20
$ echo {x,y}{1,2}
x1 x2 y1 y2
$ ls nope{1,2}.txt
ls: cannot access 'nope1.txt': No such file or directory
ls: cannot access 'nope2.txt': No such file or directory
```

Если у границы диапазона есть ведущий ноль, bash выровняет все числа: `{01..12}` даёт `01 … 12`. Каталоги `2025-1 … 2025-12` без нуля отсортируются как `2025-1, 2025-10, 2025-11, 2025-12, 2025-2`. Обрати внимание и на последний пример: файлов нет, а скобки всё равно раскрылись. Шаблон бы так не сделал.

Три приёма на каждый день:

```text
$ cp app.conf{,.bak}
$ mv app.conf{.bak,.orig}
$ mkdir -p proj/{src,docs,tests}
```

`app.conf{,.bak}` раскрывается в `app.conf app.conf.bak`, то есть в бэкап одной командой. Вторая строка переименует `app.conf.bak` в `app.conf.orig`.

Скобки раскрываются **раньше** переменных, поэтому диапазон с переменной не работает. Пробел внутри скобок тоже ломает раскрытие:

```text
$ n=3; echo {1..$n}
{1..3}
$ echo $(seq 1 $n)
1 2 3
$ echo {a, b}
{a, b}
```

| | Скобки `{a,b}` `{1..3}` | Шаблоны `*` `?` `[ ]` |
|---|---|---|
| Смотрят в ФС | нет, генерируют строки | да, только существующие имена |
| Нет совпадений | всё равно подставят | оставят шаблон как есть |
| Очередь раскрытия | первыми | последними |

## Копирование: cp {#cp}

Шаблонами мы выбираем пачки файлов, теперь будем их копировать. У `cp` три источника сюрпризов: куда ляжет копия, что сохранится (владелец, права, время) и что станет с файлами, которые уже лежат в месте назначения.

### Куда ляжет копия

Базовые правила:

1. `cp файл новое_имя` — копия под новым именем. `cp файл каталог/` — копия внутри каталога под тем же именем.
2. Если источников несколько, последний аргумент обязан быть каталогом. Иначе — `cp: target 'c' is not a directory`. Ключ `-t каталог` ставит цель первой; это удобно с `find` и `xargs`.
3. Каталог копируется только с `-r`. Без него `cp` откажется: `cp: -r not specified; omitting directory 'site'`.
4. Если цель — **существующий каталог**, источник кладётся **внутрь** него.

Последнее правило — самая частая ловушка. Возьмём статический сайт `/srv/site` (владелец alice) и сделаем бэкап дважды:

```text
$ cd /srv
$ ls -lA site
total 8
drwxr-xr-x. 2 alice alice 22 Nov  2 19:29 css
-rw-r--r--. 1 alice alice 14 May  5  2024 .htaccess
-rw-r-----. 1 alice alice 12 May  5  2024 index.html
$ cp -r site /backup/site
$ ls -A /backup/site
css  .htaccess  index.html
$ cp -r site /backup/site
$ ls -A /backup/site
css  .htaccess  index.html  site
```

В первый раз `/backup/site` не было, и копия стала им. Во второй раз каталог уже существовал, и копия легла внутрь, в `/backup/site/site`. Одна и та же команда делает разное в зависимости от состояния — в скрипте бэкапа это бомба замедленного действия.

Как обновить копию правильно:

```text
$ cp -r site/. /backup/site/
$ cp -rT site /backup/site
```

`site/.` означает «содержимое каталога, включая скрытые файлы». `-T` говорит: «цель — это сам каталог назначения, а не место, куда класть». Вариант `site/*` хуже: звёздочка не видит скрытые файлы, и `.htaccess` не скопируется:

```text
$ mkdir stage
$ cp -r site/* stage/
$ ls -A stage
css  index.html
```

Слэш на конце цели работает как предохранитель. Если каталога нет, `cp` не создаст вместо него файл с таким именем, а выдаст ошибку:

```text
$ cp site/index.html /srv/nope/
cp: cannot create regular file '/srv/nope/': Not a directory
```

### Перезапись: -i, -n, -u, -b

По умолчанию `cp` перезаписывает существующие файлы молча. Ключи это меняют:

- `-i` спрашивает: `cp: overwrite '/tmp/index.html'?`. Ответ `y` — перезаписать, всё остальное — пропустить.
- `-n` никогда не перезаписывает и ничего не говорит. Код возврата при этом 0.
- `-u` копирует, только если источник новее цели (или цели нет).
- `-b` перед перезаписью сохраняет старый файл с тильдой на конце.
- `-v` печатает, что сделано.

```text
$ ls -l src dst
dst:
total 8
-rw-r--r--. 1 root root 4 Nov  1 00:00 a.conf
-rw-r--r--. 1 root root 6 Nov  2 10:00 b.conf

src:
total 8
-rw-r--r--. 1 root root 4 Nov  2 10:00 a.conf
-rw-r--r--. 1 root root 4 Nov  1 00:00 b.conf
$ cp -uv src/* dst/
'src/a.conf' -> 'dst/a.conf'
$ cp -bv src/a.conf dst/a.conf
'src/a.conf' -> 'dst/a.conf' (backup: 'dst/a.conf~')
```

`-u` скопировал только `a.conf`: в `dst` он был старше. `b.conf` в `dst` новее источника, и его не тронули.

> **Ловушка.** У root в RHEL в `/root/.bashrc` прописаны алиасы `rm='rm -i'`, `cp='cp -i'` и `mv='mv -i'`. Поэтому root на каждую перезапись получает вопрос, а скрипт, вставленный в терминал, зависает на первом же `overwrite?`. Обойти алиас можно через `\cp` или `command cp`. Причём у `cp` ключ `-f` вопрос **не отменяет**: `cp -f` всё равно спросит, потому что `-f` у `cp` означает другое — «если цель не открывается на запись, удали её и попробуй снова». У `mv` и `rm` последний из ключей `-i`/`-f` побеждает, и `-f` вопрос отменяет.

### Что сохраняется: -p и -a

Обычная копия — это новый файл. Посмотрим, что от оригинала доживает до копии. root копирует `index.html` от alice (права 640, mtime — май 2024) тремя способами:

```text
$ cd /srv/site
$ cp index.html /tmp/c1.html
$ cp -p index.html /tmp/c2.html
$ cp -a index.html /tmp/c3.html
$ ls -l index.html /tmp/c?.html
-rw-r-----. 1 alice alice 12 May  5  2024 index.html
-rw-r-----. 1 root  root  12 Nov  2 19:17 /tmp/c1.html
-rw-r-----. 1 alice alice 12 May  5  2024 /tmp/c2.html
-rw-r-----. 1 alice alice 12 May  5  2024 /tmp/c3.html
```

| Команда | Владелец | Права | mtime |
|---|---|---|---|
| `cp` | тот, кто копирует | исходные минус umask | сейчас |
| `cp -p` | исходный | исходные | исходное |
| `cp -a` | исходный | исходные | исходное |

- Без `-p` права копии — это права оригинала минус umask. 640 при umask 022 остаются 640, а 777 станут 755. Права не «сбрасываются в 644», umask только убирает биты.
- `-p` — это `--preserve=mode,ownership,timestamps`.
- `-a` — это `-dR --preserve=all`: рекурсивно, ссылки копируются как ссылки, и вдобавок сохраняются жёсткие ссылки внутри дерева, расширенные атрибуты (xattr) и SELinux-контекст. Для бэкапов и переноса деревьев нужен именно `-a`.
- Обычный пользователь не может отдать файл другому. Поэтому `cp -p` и `cp -a` от его имени молча делают копию его собственной, без ошибки и с кодом возврата 0. Права и время при этом сохраняются. Вот alice копирует файл bob:

```text
$ cp -p /tmp/share/bob.txt ~/
$ echo $?
0
$ ls -l /tmp/share/bob.txt ~/bob.txt
-rw-r--r--. 1 alice alice 5 Jan  1  2025 /home/alice/bob.txt
-rw-r--r--. 1 bob   bob   5 Jan  1  2025 /tmp/share/bob.txt
```

### Копия поверх существующего файла

Если цель уже существует, `cp` не создаёт новый файл, а открывает старый и переписывает его содержимое. Inode, владелец и права цели остаются прежними:

```text
$ ls -li /tmp/old.html
648881 -rw-------. 1 bob bob 13 Nov  2 19:17 /tmp/old.html
$ \cp index.html /tmp/old.html
$ ls -li /tmp/old.html
648881 -rw-------. 1 bob bob 12 Nov  2 19:17 /tmp/old.html
```

Тот же inode 648881, тот же владелец bob и права 600, а содержимое новое. Если важны права оригинала, нужно `cp -p` или отдельный `chmod`. Процесс, у которого цель открыта, сразу видит новое содержимое. У `mv` всё наоборот: он заменяет имя, и под ним оказывается другой inode.

### Ссылки при копировании

- `cp ссылка куда` копирует **содержимое** цели ссылки. Получается обычный файл.
- `cp -r ссылка куда` копирует **саму ссылку**. Относительная ссылка на новом месте часто оказывается битой:

```text
$ cd /srv/app
$ cp current /srv/cur1
cp: -r not specified; omitting directory 'current'
$ cp -r current /srv/cur2
$ cp -rL current /srv/cur3
$ ls -ld /srv/cur*
lrwxrwxrwx. 1 root root 11 Nov  2 20:12 /srv/cur2 -> releases/v2
drwxr-xr-x. 4 root root 48 Nov  2 20:12 /srv/cur3
```

`/srv/cur2` указывает на `releases/v2` относительно `/srv`, а такого каталога нет. `-L` разыменовывает ссылки и копирует то, на что они указывают: `/srv/cur3` — настоящий каталог с `bin` и `conf` внутри.

Жёсткие ссылки внутри дерева `cp -r` разрывает: два имени одного файла становятся двумя отдельными файлами. `cp -a` сохраняет связь:

```text
$ ls -li h h_r h_a
h:
total 8
648949 -rw-r--r--. 2 root root 2 Nov  2 19:18 one
648949 -rw-r--r--. 2 root root 2 Nov  2 19:18 two

h_a:
total 8
648954 -rw-r--r--. 2 root root 2 Nov  2 19:18 one
648954 -rw-r--r--. 2 root root 2 Nov  2 19:18 two

h_r:
total 8
648951 -rw-r--r--. 1 root root 2 Nov  2 19:18 one
648952 -rw-r--r--. 1 root root 2 Nov  2 19:18 two
```

> **На практике.** Про SELinux. Обычный `cp` создаёт новый файл, и тот получает контекст каталога назначения. `mv` и `cp -a` уносят исходный контекст. Файл, перенесённый `mv` из домашнего каталога в `/var/www/html`, останется с типом `user_home_t`, и httpd ответит 403, хотя права в `ls -l` в порядке. Лечится командой `restorecon -Rv /var/www/html` (подробно — в главе про SELinux).

## Перемещение и переименование: mv {#mv}

`cp` всегда создаёт новый файл, то есть новый inode, и копирует в него данные. `mv` устроен иначе: в пределах одной ФС он данные вообще не трогает. Главное в `mv` — понимать, когда он переименовывает, а когда на самом деле копирует.

### Переименование

Внутри одной ФС `mv` вызывает `rename()`: переписывает строку в таблице каталога (вспомни подтему про inode). Поэтому 50-мегабайтный дамп и пятибайтный файл переименовываются одинаково мгновенно, а номер inode не меняется:

```text
$ cd /srv/data
$ ls -li dump.sql
262294 -rw-r--r--. 1 root root 52428800 Oct 30 03:00 dump.sql
$ mv -v dump.sql dump-old.sql
renamed 'dump.sql' -> 'dump-old.sql'
$ ls -li dump-old.sql
262294 -rw-r--r--. 1 root root 52428800 Oct 30 03:00 dump-old.sql
```

mtime тоже не изменился: содержимое никто не трогал. Сдвигается только ctime, и меняются mtime и ctime каталогов, в которых поменялась таблица имён.

### Между файловыми системами

Дамп на `/srv` больше не нужен, перенесём его на диск с бэкапами. Номер inode имеет смысл только внутри своей ФС, поэтому переименовать файл с `/srv` (XFS) в `/backup` (другой диск, ext4) нельзя. Ядро отвечает ошибкой `EXDEV`, и `mv` молча переходит к плану Б: копирует, а потом удаляет оригинал. `-v` это выдаёт:

```text
$ mv -v dump-old.sql /backup/
copied 'dump-old.sql' -> '/backup/dump-old.sql'
removed 'dump-old.sql'
$ ls -li /backup/dump-old.sql
30 -rw-r--r--. 1 root root 52428800 Oct 30 03:00 /backup/dump-old.sql
```

Вместо `renamed` — `copied` и `removed`, номер inode стал другим. Последствия: время работы пропорционально размеру данных, а в месте назначения нужно свободное место под полную копию. Владельца, права и времена `mv` переносит, как `cp -a`. Что бывает, если такой `mv` большого каталога оборвать, — в последней подтеме.

### Куда ляжет и что перезапишет

Правила те же, что у `cp`. Если цель — существующий каталог, источник уйдёт внутрь. `-T` велит считать цель самим каталогом. Слэш на конце цели работает как предохранитель:

```text
$ mv b nope/
mv: cannot move 'b' to 'nope/': Not a directory
```

Каталог поверх непустого каталога `mv` не кладёт. Текст ошибки зависит от ФС: XFS отвечает `File exists`, ext4 — `Directory not empty`:

```text
$ mv /srv/a2/dir /srv/b2/
mv: cannot move '/srv/a2/dir' to '/srv/b2/dir': File exists
$ mv /backup/a/dir /backup/b/
mv: cannot move '/backup/a/dir' to '/backup/b/dir': Directory not empty
```

`-i`, `-n`, `-u`, `-b`, `-v` работают так же, как у `cp`. Есть одно отличие: у `mv` ключ `-f` отменяет `-i`, в том числе из алиаса root.

### Массовое переименование

`mv *.log *.bak` не работает: `mv` получает список вида `a.log app.log b.log *.bak` и ждёт, что последний аргумент окажется каталогом:

```text
$ mv *.log *.bak
mv: target '*.bak' is not a directory
```

Переименовывают циклом или утилитой `rename` из util-linux. Её синтаксис — «что заменить, на что, в каких файлах»:

```text
$ rename -v .log .bak *.log
`a.log' -> `a.bak'
`app.log' -> `app.bak'
`b.log' -> `b.bak'
$ for f in *.bak; do
>   mv -- "$f" "${f%.bak}.old"
> done
```

В RHEL `rename` — именно из util-linux. Perl-версия с синтаксисом `rename 's/…/…/'`, знакомая по Debian и Ubuntu, здесь не работает. `${f%.bak}` отрезает от значения переменной суффикс `.bak`, а `--` защищает от имён на дефис.

### Сводка флагов cp и mv

| Флаг | cp | mv |
|---|---|---|
| `-r` | каталоги рекурсивно | ключа нет, каталоги и так |
| `-a` | архив: `-dR` + сохранить всё | — |
| `-p` | права, владелец, время | ключа нет, сохраняет и так |
| `-i` / `-n` | спросить / не перезаписывать | так же |
| `-f` | не отменяет `-i` | отменяет `-i` |
| `-u` | только если источник новее | так же |
| `-b` | бэкап `файл~` перед перезаписью | так же |
| `-v` | печатать действия | так же |
| `-T` | цель — сам каталог | так же |
| `-t DIR` | цель первым аргументом | так же |
| `-L` / `-P` | разыменовать ссылки / нет | — |
| `-l` / `-s` | жёсткая / символическая ссылка вместо копии | — |

## Удаление: rm, rmdir, unlink {#rm}

Копировать и переносить мы научились. Удаление кажется самой простой операцией, но в Linux нет корзины: `rm` необратим. При этом удаляет он вовсе не файл, а имя, и от этого зависят и права, и освобождение места.

### Файлы и каталоги

`rm файл` удаляет файл. С каталогами он работает только по явной просьбе:

```text
$ rm dir
rm: cannot remove 'dir': Is a directory
$ rm -d dir
rm: cannot remove 'dir': Directory not empty
$ rmdir dir
rmdir: failed to remove 'dir': Directory not empty
```

`rmdir` и `rm -d` удаляют только **пустые** каталоги. Это удобно как проверка: если внутри что-то осталось, ничего не пропадёт. `rm -r` удаляет каталог со всем содержимым. `rmdir -p` удаляет цепочку пустых каталогов снизу вверх, а `-v` у обеих команд рассказывает, что сделано:

```text
$ rmdir -pv x/y/z
rmdir: removing directory, 'x/y/z'
rmdir: removing directory, 'x/y'
rmdir: removing directory, 'x'
$ rm -rv d
removed directory 'd/e/f'
removed directory 'd/e'
removed directory 'd'
```

### -f, -i и -I

- `-f` (force) не спрашивает ничего и молчит про несуществующие файлы: `rm -f nope` завершится без ошибки и с кодом 0.
- `-i` спрашивает про каждый файл: `rm: remove regular empty file 'b'?`.
- `-I` спрашивает один раз, если файлов больше трёх или удаление рекурсивное. Это компромисс между безопасностью и занудством:

```text
rm: remove 4 arguments?
rm: remove 1 argument recursively?
```

Ключи действуют по принципу «последний побеждает». Алиас root `rm='rm -i'` превращает `rm -rf dir` в `rm -i -rf dir`, а `-f` стоит позже и отменяет вопросы. Поэтому алиас защищает только от `rm файл`, а от `rm -rf` — нет.

### Защищённые от записи файлы

Если у файла нет права записи, `rm` переспросит: `rm: remove write-protected regular file 'root.conf'?`. Но только при двух условиях: удаляет не root, и стандартный ввод — терминал. В cron, в пайпе и в скрипте, запущенном без терминала, вопроса не будет, и файл удалится молча. root таких вопросов не получает вовсе.

### Удаление — это unlink

Вспомни подтему про inode: имя хранится в каталоге. `rm` вызывает `unlink()` — убирает строку «имя → inode» из таблицы каталога. Значит, право на удаление определяется правами на **каталог** (нужны `w` и `x`), а не на файл. alice удаляет файл root у себя в домашнем каталоге (`rm` только переспросил, ведь права записи в файл у неё нет), но не может удалить свой собственный файл в чужом каталоге:

```text
$ ls -l ~/root.conf /srv/shared/alice.txt
-rw-r--r--. 1 root  root 4 Nov  2 19:20 /home/alice/root.conf
-rw-r--r--. 1 alice root 2 Nov  2 19:20 /srv/shared/alice.txt
$ rm -v ~/root.conf
rm: remove write-protected regular file '/home/alice/root.conf'? y
removed '/home/alice/root.conf'
$ rm /srv/shared/alice.txt
rm: cannot remove '/srv/shared/alice.txt': Permission denied
```

Как sticky-бит на `/tmp` не даёт удалять чужие файлы при общем праве записи — в главе «Права».

Данные при этом освобождаются не в момент `rm`. Inode и блоки возвращаются ФС, только когда у файла не осталось ни одного имени (жёсткие ссылки — следующая подтема) **и** его не держит открытым ни один процесс. На этом построен главный сюрприз — «удалил лог, а место не освободилось» — разобранный в последней подтеме. Утилита `unlink файл` делает ровно один такой вызов: удаляет одно имя, без ключей и без шаблонов.

> **Важно.** `rm` не затирает данные, а только освобождает блоки. Пока их не перезапишут, содержимое можно восстановить специальными средствами. Для надёжного уничтожения есть `shred`, но на журналируемых ФС и SSD и он не даёт гарантий.

### Имя, которое начинается с дефиса

Загрузчик с багом создал в каталоге файл `-rf`. Попробуем удалить его в лоб:

```text
$ rm -rf
$ ls
a.txt  logs  -rf
```

Ничего не произошло, даже ошибки нет: `rm` понял `-rf` как ключи `-r -f`, а `-f` без имён файлов — законная команда, которая ничего не делает. С кавычками будет то же самое (их снимает bash). Работают два способа, и `rm --help` прямо про них пишет:

```text
$ rm -- -rf
$ rm ./-rf
```

GNU `rm` даже подсказывает, если имя с дефисом оказалось неизвестным ключом и такой файл существует:

```text
$ rm -x
rm: invalid option -- 'x'
Try 'rm ./-x' to remove the file '-x'.
Try 'rm --help' for more information.
```

### rm * и файл с именем -rf

Теперь страшное. В каталоге лежат `a.txt`, каталог `logs` и тот самый файл `-rf`. Что сделает `rm *`? Посмотрим через `echo`, во что раскроется шаблон:

```text
$ echo rm *
rm a.txt logs -rf
```

GNU `rm` понимает ключи в любом месте командной строки, поэтому это `rm -rf a.txt logs`. Удалится всё, **кроме** самого `-rf`, и каталог `logs` уйдёт рекурсивно. Алиас `rm -i` не спасёт: `-f` из имени файла стоит позже и отменит вопросы. Безопасные варианты, в которых имя не может стать ключом:

```text
$ echo rm -- *
rm -- a.txt logs -rf
$ echo rm ./*
rm ./a.txt ./logs ./-rf
```

> **На практике.** Если в каталог пишут внешние клиенты (загрузки, почта, выгрузки), имена там могут быть любыми. Удаляй через `./*`, `--` или `find … -delete`, которому имена безразличны.

### Пустая переменная

```bash
DIR=
rm -rf "$DIR"/     # станет rm -rf /
rm -rf "$DIR"/*    # станет rm -rf /bin /boot …
```

Первую строку остановит встроенная защита `--preserve-root`:

```text
rm: it is dangerous to operate recursively on '/'
rm: use --no-preserve-root to override this failsafe
```

Вторую — нет: звёздочка раскроется в `/bin /boot /dev /etc …`, и ни один аргумент не будет равен `/`. Защита — подстановка `${DIR:?}`: если переменная пустая или не задана, bash остановит скрипт ещё до `rm`:

```bash
#!/bin/bash
DIR=
rm -rf "${DIR:?}"/*
```

```text
./clean.sh: line 3: DIR: parameter null or not set
```

`set -u` тут не поможет: он ловит только **незаданные** переменные, а `DIR=` задана, просто пуста.

### Что ещё rm не станет делать

`rm -r .` и `rm -r ..` отказываются работать: `rm: refusing to remove '.' or '..' directory: skipping '.'`. Если внутри удаляемого дерева есть точка монтирования (например, в chroot смонтированы `/proc` или bind-каталог с данными), `rm -r` спустится и туда. Ключ `--one-file-system` не даёт ему выходить за пределы ФС, с которой он начал.

## Ссылки: жёсткие и символические {#links}

Мы выяснили, что `rm` удаляет имя, а не файл. Значит, у одного файла может быть несколько имён, и файл живёт, пока осталось хотя бы одно из них. Это жёсткие ссылки. Символические устроены совсем иначе: это отдельный маленький файл с путём внутри.

### Жёсткая ссылка — второе имя того же inode

```text
$ cd /srv/links
$ ln app.conf app.hard
$ ln -s app.conf app.soft
$ ls -li
total 8
155 -rw-r--r--. 2 root root 10 Nov  2 19:20 app.conf
155 -rw-r--r--. 2 root root 10 Nov  2 19:20 app.hard
156 lrwxrwxrwx. 1 root root  8 Nov  2 19:20 app.soft -> app.conf
```

`app.conf` и `app.hard` — два имени inode 155, и счётчик ссылок у него стал 2. Ни одно из имён не «главное»: это просто две строки в таблице каталога. Запись через одно имя видна через другое — данные-то одни:

```text
$ echo "port=9090" >> app.hard
$ cat app.conf
port=8080
port=9090
```

А теперь переименуем «оригинал»:

```text
$ mv app.conf app.conf.orig
$ ls -li
total 8
155 -rw-r--r--. 2 root root 20 Nov  2 19:20 app.conf.orig
155 -rw-r--r--. 2 root root 20 Nov  2 19:20 app.hard
156 lrwxrwxrwx. 1 root root  8 Nov  2 19:20 app.soft -> app.conf
$ cat app.hard
port=8080
port=9090
$ cat app.soft
cat: app.soft: No such file or directory
```

Жёсткой ссылке всё равно: она указывает на inode, а не на имя. Символическая хранит **путь** `app.conf`, по этому пути теперь пусто, и ссылка стала битой. Так же было бы после `rm app.conf`: данные доступны через `app.hard`, пока счётчик не дойдёт до нуля.

У жёстких ссылок два ограничения, и оба следуют из устройства inode:

```text
$ ln d d2
ln: d: hard link not allowed for directory
$ ln /srv/links/app.conf /backup/app.conf
ln: failed to create hard link '/backup/app.conf' => '/srv/links/app.conf': Invalid cross-device link
```

На каталоги нельзя: иначе в дереве появились бы циклы, и `find`, `du`, `rm -r` ходили бы по кругу. Между ФС нельзя: номер inode 155 на XFS ничего не значит для ext4 в `/backup`.

### Символическая ссылка — файл с путём

Символическая ссылка — отдельный inode (у `app.soft` номер 156), внутри которого записан путь. Размер ссылки — длина этого пути: у `app.soft` это 8 байт (`app.conf`). Права ссылки всегда `lrwxrwxrwx` и ни на что не влияют: доступ проверяется по правам цели. Ссылка может вести на каталог, на другую ФС и даже в никуда.

**Относительный путь в ссылке считается от каталога, где лежит сама ссылка**, а не от того, где ты был, когда её создавал. Это самая частая ошибка с `ln -s`:

```text
$ cd /srv/links
$ ln -s app.conf /etc/myapp.conf
$ ls -l /etc/myapp.conf
lrwxrwxrwx. 1 root root 8 Nov  2 19:20 /etc/myapp.conf -> app.conf
$ cat /etc/myapp.conf
cat: /etc/myapp.conf: No such file or directory
```

Ссылка ищет `app.conf` рядом с собой, то есть `/etc/app.conf`, а его нет. Ещё забавнее, если имя ссылки совпадает с целью:

```text
$ ln -s app.conf /tmp/app.conf
$ cat /tmp/app.conf
cat: /tmp/app.conf: Too many levels of symbolic links
```

`/tmp/app.conf` указывает на `app.conf` в `/tmp`, то есть на саму себя. Ядро бросает поиск после 40 переходов.

Правильно — абсолютный путь или `ln -sr`. Ключ `-r` сам посчитает относительный путь от места ссылки:

```text
$ ln -s /srv/links/app.conf /etc/myapp2.conf
$ ln -sr app.conf /etc/myapp3.conf
$ ls -l /etc/myapp3.conf
lrwxrwxrwx. 1 root root 21 Nov  2 19:20 /etc/myapp3.conf -> ../srv/links/app.conf
```

Относительные ссылки хороши, когда дерево переносят целиком: `current -> releases/v2` продолжит работать в любой копии `/srv/app`. Абсолютные хороши, когда переносят саму ссылку.

### Куда ведёт ссылка: readlink и realpath

```text
$ readlink /etc/myapp3.conf
../srv/links/app.conf
$ readlink -f /etc/myapp3.conf
/srv/links/app.conf
$ readlink -f /etc/myapp.conf; echo $?
/etc/app.conf
0
$ readlink -e /etc/myapp.conf; echo $?
1
```

Без ключей `readlink` выводит путь, записанный в ссылке, как есть. `-f` проходит всю цепочку ссылок и выдаёт канонический абсолютный путь, даже если последнего компонента нет. Поэтому для битой ссылки он вернёт путь к несуществующему файлу с кодом 0. `-e` требует, чтобы существовало всё, — для проверки в скрипте нужен именно он. `realpath` по умолчанию работает как `readlink -f`.

Битые ссылки ищет `find`:

```text
$ find /etc -maxdepth 1 -xtype l
/etc/myapp.conf
```

`-xtype l` означает: «после разыменования это всё ещё ссылка», то есть цель не найдена.

### Ссылка на каталог: деплой через current

Схема `releases/v1`, `releases/v2` плюс ссылка `current` — стандартный способ выкатки: новая версия раскладывается рядом, а переключение — это смена одной ссылки. И тут ловушка:

```text
$ cd /srv/app
$ ls -l current
lrwxrwxrwx. 1 root root 11 Nov  2 09:31 current -> releases/v2
$ ln -sf releases/v3 current
$ ls -l current
lrwxrwxrwx. 1 root root 11 Nov  2 09:31 current -> releases/v2
$ ls -l releases/v2
total 0
drwxr-xr-x. 2 root root  6 Nov  2 09:30 bin
drwxr-xr-x. 2 root root 34 Nov  2 19:36 conf
-rw-r--r--. 1 root root  0 Nov  2 09:30 install.log
lrwxrwxrwx. 1 root root 11 Nov  2 19:41 v3 -> releases/v3
```

`ln -sf` ничего не переключил, а создал ссылку `v3` внутри `releases/v2`. Если последний аргумент — ссылка на каталог, `ln` (как `cp` и `mv`) считает его каталогом и кладёт новую ссылку внутрь. Ключ `-n` велит не разыменовывать цель:

```text
$ ln -sfn releases/v3 current
$ ls -l current
lrwxrwxrwx. 1 root root 11 Nov  2 19:41 current -> releases/v3
```

`ln -sfn` (или `ln -sfT`) — правильный способ переключать такие ссылки.

> **Ловушка.** Слэш на конце меняет смысл. `ls -l current` показывает ссылку, `ls -l current/` — содержимое каталога. `rm current` удалит ссылку, а `rm -r current/` пойдёт **внутрь** и удалит содержимое `releases/v2`. Подробности — в последней подтеме.

### Сравнение

| | Жёсткая (`ln`) | Символическая (`ln -s`) |
|---|---|---|
| Что это | ещё одно имя того же inode | отдельный файл с путём |
| Свой inode | нет | да |
| На каталог | нельзя | можно |
| На другую ФС | нельзя | можно |
| Цель удалили или переименовали | данные живы | ссылка битая |
| Права | общие с файлом | свои не важны, `lrwxrwxrwx` |
| Как увидеть | счётчик больше 1, одинаковый номер в `ls -i` | `l` в `ls -l`, стрелка `->` |

Найти все имена одного файла можно по номеру inode: `find /srv -xdev -inum 155`. `-xdev` нужен потому, что номер уникален только внутри одной ФС.

## Три времени файла {#times}

В листингах уже мелькали mtime, atime и ctime. Пора разобраться, что каждое из них значит. Это не академический вопрос: «кто и когда поменял конфиг», «какие логи старше 30 дней», «что изменилось после деплоя» — всё это вопросы про времена файла.

### Четыре метки в inode

| Метка | В `stat` | Когда меняется | В `ls` |
|---|---|---|---|
| atime | Access | содержимое прочитали | `-lu` |
| mtime | Modify | содержимое изменили | `-l` |
| ctime | Change | изменился inode: права, владелец, имя, число ссылок, а также при любом изменении mtime | `-lc` |
| btime | Birth | файл создан | `-l --time=birth` |

**ctime — это не «creation»**, а «change», изменение inode. Время создания — `Birth`: XFS и ext4 его хранят, а `stat` в RHEL 9 его показывает.

### Эксперимент

Проследим за `app.conf` (содержимое последний раз меняли 28 октября). Чтобы не печатать `stat` целиком, заведём короткий алиас:

```text
$ alias t="stat --printf='A %x\nM %y\nC %z\n'"
$ t app.conf
A 2026-10-28 16:40:00.000000000 +0000
M 2026-10-28 16:40:00.000000000 +0000
C 2026-11-02 19:28:40.344564142 +0000
```

Читаем файл два раза подряд:

```text
$ cat app.conf > /dev/null
$ t app.conf
A 2026-11-02 19:28:45.504564024 +0000
M 2026-10-28 16:40:00.000000000 +0000
C 2026-11-02 19:28:40.344564142 +0000
$ cat app.conf > /dev/null
$ t app.conf
A 2026-11-02 19:28:45.504564024 +0000
M 2026-10-28 16:40:00.000000000 +0000
C 2026-11-02 19:28:40.344564142 +0000
```

Первое чтение сдвинуло atime, а второе — нет. Это не ошибка, а `relatime`, о нём ниже. Теперь допишем строку, потом сменим права, потом переименуем туда и обратно:

```text
$ echo "key13 = 13" >> app.conf
$ t app.conf
A 2026-11-02 19:28:45.504564024 +0000
M 2026-11-02 19:28:49.524563932 +0000
C 2026-11-02 19:28:49.524563932 +0000
$ chmod 640 app.conf
$ t app.conf
A 2026-11-02 19:28:45.504564024 +0000
M 2026-11-02 19:28:49.524563932 +0000
C 2026-11-02 19:28:51.532563886 +0000
$ mv app.conf app.new; mv app.new app.conf
$ t app.conf
A 2026-11-02 19:28:45.504564024 +0000
M 2026-11-02 19:28:49.524563932 +0000
C 2026-11-02 19:28:53.544563840 +0000
```

Запись сдвинула mtime и ctime, а `chmod` и переименование — только ctime. Итог:

| Действие | atime | mtime | ctime |
|---|---|---|---|
| `cat`, `less`, `grep` (чтение) | да, с оговоркой relatime | — | — |
| `>>`, `>`, правка редактором | — | да | да |
| `chmod`, `chown` | — | — | да |
| `mv` в пределах ФС | — | — | да |
| `ln` (новая жёсткая ссылка) | — | — | да |
| `touch` | да | да | да |
| `ls -l`, `stat` | — | — | — |

У каталога mtime меняется, когда меняется его таблица имён: создали, удалили или переименовали файл внутри. Правка содержимого файла mtime каталога не трогает.

```text
$ stat -c '%s %y' .
6 2026-11-02 19:41:21.920546723 +0000
$ touch new
$ stat -c '%s %y' .
17 2026-11-02 19:41:22.132546718 +0000
```

В пустом каталоге появилось имя: таблица выросла с 6 до 17 байт, и mtime каталога сдвинулся.

### relatime: почему atime «врёт»

Если бы ядро писало atime на каждое чтение, каждое чтение превращалось бы в запись на диск. Поэтому с Linux 2.6.30 по умолчанию действует `relatime`: atime обновляется, только если он был не новее mtime или ctime, или если ему больше суток (по `man 8 mount`). В примере выше первое чтение обновило atime (он был равен mtime), а второе — нет (atime уже был новее обоих). Опция видна в параметрах монтирования:

```text
$ findmnt -no OPTIONS /srv
rw,relatime,seclabel,attr2,inode64,logbufs=8,logbsize=32k,noquota
```

Есть и `noatime`: atime не обновляется вовсе, его иногда включают на нагруженных ФС с базами. Вывод: atime показывает «читали ли файл хоть раз после последнего изменения или за последние сутки». Журналом обращений он не является, для этого есть auditd.

### Как смотреть времена

- `ls -l` показывает mtime, `ls -lu` — atime, `ls -lc` — ctime, `ls -l --time=birth` — время создания. Сортировку по нужному времени включает `-t` (ловушка с `-lu` разобрана в подтеме про ls).
- `ls -l --full-time` выводит полную метку с наносекундами и часовым поясом.
- `stat` показывает все четыре сразу, `stat -c` — выборочно: `%x %y %z %w` (atime, mtime, ctime, birth) или `%X %Y %Z %W` в секундах с 1970 года. Секунды удобно сравнивать в скриптах.

### touch: поставить нужное время

```text
$ touch -d "2025-03-10 09:00" a
$ touch -t 202503100900 b
$ touch -d "2 days ago" c
$ touch -r a d
$ ls -l a b c d
-rw-r--r--. 1 root root 0 Mar 10  2025 a
-rw-r--r--. 1 root root 0 Mar 10  2025 b
-rw-r--r--. 1 root root 0 Oct 31 19:21 c
-rw-r--r--. 1 root root 0 Mar 10  2025 d
```

- `-d СТРОКА` понимает почти любую дату: `"2025-03-10 09:00"`, `"2 days ago"`, `"yesterday"`.
- `-t [[CC]YY]MMDDhhmm[.ss]` — компактный формат.
- `-r файл` берёт время у другого файла. Это удобно, чтобы вернуть время после правки или создать метку для `find -newer`.
- `-a` и `-m` меняют только atime или только mtime.
- `-c` не создаёт файл, если его нет. `-h` меняет время самой ссылки, а не цели.

```text
$ touch -a -d "2026-01-01" a
$ stat a | tail -4
Access: 2026-01-01 00:00:00.000000000 +0000
Modify: 2025-03-10 09:00:00.000000000 +0000
Change: 2026-11-02 19:21:37.376573816 +0000
 Birth: 2026-11-02 19:21:37.356573817 +0000
```

> **Важно.** ctime и btime руками не поставить. Любая операция с inode, включая сам `touch -d`, выставляет ctime в «сейчас», а btime не меняется никогда. Поэтому файл, «состаренный» через `touch -d`, выдаёт себя свежим ctime. Если mtime в прошлом, а ctime сегодня, значит, с файлом что-то делали сегодня.

### Где времена работают

- **Поиск по возрасту.** `find /var/log -mtime +30` (не меняли больше 30 дней), `find -mmin -10`, `find -newer метка` — по mtime. Подробно — в главе «Поиск».
- **«Кто менял права на конфиг?»** — это вопрос про ctime: `ls -lc`, `stat`.
- **Копирование.** `cp` ставит копии mtime «сейчас», `cp -p` и `cp -a` сохраняют исходное. `mv` mtime не трогает, даже между ФС. `rsync` по умолчанию решает, что копировать, по mtime и размеру. Поэтому после `cp` без `-p` он сочтёт изменёнными все файлы и пройдётся по каждому.

## Когда всё идёт не так {#deep}

Основное позади. Эта подтема — про ситуации, в которых знание inode, `unlink` и `rename` отличает «пять минут» от «полдня с паникой». Каждый сценарий воспроизведён на нашем сервере.

### Удалил лог, а место не освободилось

Ночью пришёл алерт: `/srv` заполнен на 78 %. Виновник нашёлся быстро — `debug.log` приложения `myapp` на 150 МБ. Удаляем его:

```text
$ df -h /srv
Filesystem      Size  Used Avail Use% Mounted on
/dev/loop0      236M  183M   54M  78% /srv
$ rm /srv/app/logs/debug.log
$ df -h /srv
Filesystem      Size  Used Avail Use% Mounted on
/dev/loop0      236M  183M   54M  78% /srv
$ du -sh /srv
2.4M    /srv
```

Файла нет, `du` насчитал 2,4 МБ, а `df` по-прежнему видит 183 МБ занятыми. Вспомни подтему про rm: `rm` удалил **имя**, и у inode не осталось ни одного (`Links: 0`). Но `myapp` держит файл открытым и продолжает в него писать. Пока последний дескриптор не закрыт, ядро блоки не освобождает. `du` обходит имена в каталогах и такого файла не видит, а `df` спрашивает саму ФС о занятых блоках. Расхождение между `df` и `du` — главный симптом этой ситуации.

Ищем, кто держит удалённые файлы. Каждый открытый файл процесса виден как ссылка в `/proc/PID/fd`, и у удалённых к цели дописано `(deleted)`:

```text
$ find /proc/[0-9]*/fd -lname '*(deleted)' 2>/dev/null
/proc/1916/fd/3
$ ls -l /proc/1916/fd/3
l-wx------. 1 root root 64 Nov  2 19:23 /proc/1916/fd/3 -> '/srv/app/logs/debug.log (deleted)'
```

То же самое удобнее показывает `lsof +L1` («открытые файлы, у которых меньше одной ссылки»), если пакет `lsof` установлен:

```text
$ lsof +L1
COMMAND  PID USER   FD   TYPE DEVICE  SIZE/OFF NLINK   NODE NAME
myapp   1916 root    3w   REG    7,0 157286400     0 262290 /srv/app/logs/debug.log (deleted)
```

`NLINK 0` — имён нет, `SIZE/OFF` — 150 МБ, которые по-прежнему заняты.

Как освободить место:

1. **Правильно** — перезапустить сервис или попросить его переоткрыть логи (`systemctl restart`, `reload`, сигнал, если приложение его понимает). Процесс закроет дескриптор, и ядро освободит блоки.
2. **Если перезапуск сейчас невозможен** — обрезать файл через дескриптор. Запись в `/proc/PID/fd/N` идёт в тот самый удалённый файл:

```text
$ : > /proc/1916/fd/3
$ df -h /srv
Filesystem      Size  Used Avail Use% Mounted on
/dev/loop0      236M   23M  214M  10% /srv
```

Есть нюанс. Если программа открыла файл без режима дозаписи (`O_APPEND`), она продолжит писать со старого смещения в 150 МБ. Файл снова «вырастет» до прежнего размера, только начало у него будет дырой (про дыры — ниже), и место она не займёт.

> **На практике.** Лог, в который пишет живой процесс, чистят через `: > app.log` или `truncate -s 0 app.log`, а не через `rm`. В logrotate для таких приложений есть два пути: `copytruncate` (скопировать и обрезать файл на месте) или `create` вместе с `postrotate`, где сервису посылают `reload`, чтобы он переоткрыл файл.

### Вернуть удалённый файл, пока процесс жив

Есть у этого и приятная сторона. Если удалили нужный файл, а процесс всё ещё держит его открытым, содержимое можно достать через `/proc`. Вот `app.conf` удалили по ошибке, а долгоживущий процесс его ещё не закрыл:

```text
$ ls -l /proc/1971/fd/3
lr-x------. 1 root root 64 Nov  2 19:23 /proc/1971/fd/3 -> '/srv/app/app.conf (deleted)'
$ cp /proc/1971/fd/3 /srv/app/app.conf
$ head -2 /srv/app/app.conf
key1 = value number 1
key2 = value number 2
```

Получилась новая копия: права, владельца и SELinux-контекст придётся вернуть руками. Работает это только пока процесс жив и дескриптор открыт. Большинство сервисов закрывают конфиг сразу после чтения, а вот базы данных и логи обычно держат открытыми.

### Место есть, а файл не создаётся

Очередь сообщений в `/var/spool/app` (ext4) перестала принимать новые задания:

```text
$ cd /var/spool/app
$ echo "job" > queue/msg-1001
bash: queue/msg-1001: No space left on device
$ touch sessions/s7
touch: cannot touch 'sessions/s7': No space left on device
$ df -h .
Filesystem      Size  Used Avail Use% Mounted on
/dev/loop2       16M  424K   15M   3% /var/spool/app
$ df -i .
Filesystem     Inodes IUsed IFree IUse% Mounted on
/dev/loop2        112   112     0  100% /var/spool/app
```

Места 97 % свободно, но кончились **inode**: каждому файлу, даже пустому, нужен свой. Ошибка при этом та же, что при нехватке места, — `No space left on device`, поэтому `df -h` сбивает с толку. Обычные виновники — миллионы мелких файлов: сессии PHP, почтовая очередь, кеш, неочищаемые временные файлы. Найти каталог, где их больше всего, помогает `du --inodes`:

```text
$ du --inodes -s /var/spool/app/*
1       /var/spool/app/lost+found
92      /var/spool/app/queue
8       /var/spool/app/sessions
```

Дальше удаляют мусор (`find queue -mtime +7 -delete`) и чинят причину. У ext4 число inode задаётся при создании ФС (`mkfs.ext4 -N` или `-i`) и потом не растёт. XFS — ФС по умолчанию в RHEL 9 — выделяет inode динамически, в пределах доли места (`imaxpct` в выводе `xfs_info`), поэтому на ней такое случается редко, но тоже бывает.

### ls говорит «гигабайт», du — «ноль»

```text
$ cd /srv
$ truncate -s 1G disk.img
$ ls -lh disk.img
-rw-r--r--. 1 root root 1.0G Nov  2 19:24 disk.img
$ du -h disk.img
0       disk.img
$ stat disk.img | head -2
  File: disk.img
  Size: 1073741824      Blocks: 0          IO Block: 4096   regular file
```

Это **разреженный** (sparse) файл. Его размер — 1 ГиБ, но в него ни разу не писали, и ФС не выделила ни одного блока. Непрописанные участки называются дырами, при чтении они отдают нули. `ls -l` и `Size` в `stat` показывают логический размер, а `du` и `Blocks` — реально занятое место. `du --apparent-size` выдаст гигабайт, как `ls`. Разреженными бывают образы дисков виртуальных машин, файлы баз данных, core-дампы.

Опасность — в копировании. `cp` по умолчанию узнаёт дыры и сохраняет их (`--sparse=auto`), а наивное копирование записывает нули честно:

```text
$ cp disk.img copy.img
$ du -h copy.img
0       copy.img
$ cat disk.img > cat.img
cat: write error: No space left on device
```

Образ, занимавший ноль, при копировании через `cat` превратился в гигабайт нулей и забил `/srv` на 236 МБ. Так же ведут себя многие сетевые способы копирования без поддержки разреженных файлов. Обратная операция — `fallocate -l 1G file`: она выделяет блоки по-настоящему, такой файл гарантированно занимает место.

### Имена с переводом строки и прочей грязью

В имени разрешено всё, кроме `/` и нулевого байта, в том числе перевод строки и пробелы по краям. В каталоге три файла:

```text
$ ls
'bad'$'\n''name.txt'   report.txt  '  spaces  '
$ ls | wc -l
4
$ ls -b
bad\nname.txt  report.txt  \ \ spaces\ \ 
$ find . -type f
./report.txt
./  spaces  
./bad?name.txt
```

В терминале `ls` честно показал имена в синтаксисе bash: `$'\n'` — это перевод строки. Но в пайпе имена идут как есть, и `wc -l` насчитал 4 «файла». `-b` показывает невидимые символы escape-последовательностями, а `find` в терминале заменяет их на `?`. Отсюда правила для скриптов:

- никогда не разбирай вывод `ls`; перебирай файлы шаблоном: `for f in *; do …; done`, и всегда с `"$f"` в кавычках;
- в пайпах используй нулевой байт как разделитель: `find … -print0` вместе с `xargs -0`, либо `find … -exec команда {} +`;
- файл с невводимым именем удаляй по номеру inode.

```text
$ ls -i
648584 'bad'$'\n''name.txt'  648567  report.txt  648599 '  spaces  '
$ find . -inum 648584 -delete
$ ls -b
report.txt  \ \ spaces\ \ 
```

### rm -r по ссылке со слэшем

`link` — ссылка на каталог `target`, в котором лежат `f1` и `f2`. Хотели удалить ссылку, но по привычке поставили слэш на конце:

```text
$ ls -l link
lrwxrwxrwx. 1 root root 6 Nov  2 19:21 link -> target
$ rm link/
rm: cannot remove 'link/': Is a directory
$ rm -r link/
rm: cannot remove 'link/': Not a directory
$ ls -A target
```

`ls -A target` ничего не вывел. Ошибка выглядит как неудача, но ущерб уже нанесён. Слэш на конце заставляет ядро пройти по ссылке. `rm -r` спустился в `target`, удалил `f1` и `f2` и только на последнем шаге попытался удалить каталог `link/` — а это ссылка, отсюда `Not a directory`. Ссылка осталась, а каталог `target` теперь пуст. Ссылку удаляют без слэша: `rm link` или `unlink link`.

### mv каталога между ФС и обрыв

Мы уже видели, что между ФС `mv` копирует и удаляет. Важен порядок. Вот что делает `mv /srv/data/dir /backup/` на уровне системных вызовов (снято `strace`, показаны только `mkdir` и `unlinkat`):

```text
mkdir("/backup/dir", 0700)              = 0
mkdir("/backup/dir/sub", 0700)          = 0
unlinkat(5, "f1", 0)                    = 0
unlinkat(4, "sub", AT_REMOVEDIR)        = 0
unlinkat(4, "f2", 0)                    = 0
unlinkat(AT_FDCWD, "/srv/data/dir", AT_REMOVEDIR) = 0
+++ exited with 0 +++
```

Сначала `mv` пробует `renameat2()`, получает `EXDEV` и копирует **всё** дерево целиком: каталоги, между ними файлы, затем права и времена. Удаление источника начинается, только когда копия готова. Что это значит для каталога в сотни гигабайт:

- **Обрыв во время копирования** (упала SSH-сессия, кончилось место, процесс убили): источник цел, а в месте назначения лежит неполная копия. Приложение, если оно смотрит в новое место, видит половину файлов.
- **Обрыв во время удаления**: копия в месте назначения полная, а источник удалён частично. Остатки источника придётся сверять с копией и удалять вручную.
- **Повторный запуск** на неполную копию не «докачивает», а падает:

```text
$ mv /srv/data/dir /backup/
mv: inter-device move failed: '/srv/data/dir' to '/backup/dir'; unable to remove target: Directory not empty
```

Вдобавок на всё время копирования в месте назначения нужно свободное место под полную копию, а файлы, изменённые в процессе, могут уехать в промежуточном состоянии.

Безопасный порядок для больших данных: скопировать (`cp -a` или `rsync -aHAX`, который умеет докачивать), сверить (`diff -r`, сравнить `du -s` и число файлов) и только потом удалить источник. Запускать всё это лучше в `tmux` или `screen`, чтобы обрыв SSH не убил процесс. В пределах одной ФС `mv` атомарен: это один вызов `rename()`, и он либо прошёл, либо нет.

## Шпаргалка {#cheatsheet}

### Навигация и пути

| Команда | Что делает |
|---|---|
| `cd -` | в предыдущий каталог |
| `cd` | домой |
| `~alice`, `~-` | домой к alice; предыдущий каталог |
| `pwd -P` | физический путь без ссылок |
| `cd -P` | перейти по физическому пути |
| `realpath путь` | канонический абсолютный путь |

### ls

| Команда | Что делает |
|---|---|
| `ls -la` | всё, включая скрытые, длинно |
| `ls -A` | скрытые, без `.` и `..` |
| `ls -ld dir` | сам каталог |
| `ls -d */` | только подкаталоги |
| `ls -ltr` | по mtime, свежие внизу |
| `ls -lS` | по размеру, большие сверху |
| `ls -lh` | размеры в K, M, G |
| `ls -ltu` | по atime (`-lu` только показывает) |
| `ls -ltc` | по ctime |
| `ls -l --time=birth` | время создания |
| `ls -l --full-time` | точное время |
| `ls -li` | с номерами inode |
| `ls -n` | uid и gid числами |
| `ls -v` | `app.log.2` раньше `app.log.10` |
| `ls -F` | значки типа: `/` `*` `@` `=` |
| `ls -Z` | SELinux-контекст |

Символ после прав в `ls -l`: `.` — есть SELinux-контекст, `+` — есть ACL.

### Inode и тип

| Команда | Что делает |
|---|---|
| `stat f` | весь inode |
| `stat -c '%i %h %s %U %a' f` | выборочно |
| `stat -L link` | цель ссылки |
| `df -i` | занятые inode |
| `file f` | тип по содержимому |
| `find / -xdev -inum N` | все имена inode N |

### Создание и чтение

| Команда | Что делает |
|---|---|
| `touch f` | создать пустой или обновить время |
| `: > f` | обнулить файл, сохранив inode |
| `set -o noclobber` | запретить `>` по существующему |
| `mkdir -p a/b/c` | цепочка, без ошибки, если есть |
| `mkdir -m 700 d` | права сразу, без umask |
| `cat -A f` | показать `^I`, `^M`, `$` |
| `head -n -5 f` | всё, кроме последних 5 строк |
| `tail -n +2 f` | всё со 2-й строки |
| `tail -F log` | следить по имени, переживает ротацию |
| `wc -l < f` | число строк, без имени |

### Шаблоны

| Шаблон | Что значит |
|---|---|
| `*` `?` `[a-z]` `[!x]` | строка, символ, диапазон, не x |
| `.[!.]*` | скрытые, без `.` и `..` |
| `shopt -s dotglob` | `*` берёт скрытые |
| `shopt -s nullglob` | нет совпадений — шаблон исчезает |
| `shopt -s failglob` | нет совпадений — ошибка |
| `shopt -s extglob` | `!(*.log)` — всё, кроме |
| `{a,b}` `{01..12}` | генерация строк, не смотрит в ФС |
| `cp f{,.bak}` | бэкап одной командой |

### cp и mv

| Команда | Что делает |
|---|---|
| `cp -a src dst` | архивная копия: всё сохранить |
| `cp -r src/. dst/` | содержимое в существующий каталог |
| `cp -rT src dst` | то же: цель — сам каталог |
| `cp -u`, `cp -n` | только новее; не перезаписывать |
| `\cp`, `command cp` | обойти алиас `cp -i` у root |
| `mv -T a b` | b — сам каталог, не «внутрь» |
| `mv -v` | `renamed` в пределах ФС, `copied` и `removed` между ФС |
| `rename .log .bak *.log` | массовое переименование |

### rm и ссылки

| Команда | Что делает |
|---|---|
| `rm -- -rf`, `rm ./-rf` | файл с именем на дефис |
| `rm -I` | один вопрос на пачку |
| `rm -r --one-file-system` | не выходить за пределы ФС |
| `"${DIR:?}"/*` | остановить скрипт при пустой переменной |
| `ln f hard` | жёсткая ссылка |
| `ln -s /abs/path link` | символическая, абсолютная |
| `ln -sr f /path/link` | символическая, относительная, посчитана верно |
| `ln -sfn new current` | переключить ссылку на каталог |
| `readlink -f`, `readlink -e` | канонический путь; с проверкой |
| `find -xtype l` | битые ссылки |

### Времена

| Что | Как |
|---|---|
| atime / mtime / ctime | `ls -lu` / `ls -l` / `ls -lc` |
| все сразу | `stat f` |
| поставить время | `touch -d "2025-03-10 09:00" f` |
| как у другого файла | `touch -r ref f` |
| только atime / mtime | `touch -a` / `touch -m` |
| ctime и btime | руками не ставятся |

### Траблшутинг

| Симптом | Что смотреть |
|---|---|
| `df` занято, `du` нет | `lsof +L1`, `find /proc/*/fd -lname '*(deleted)'` |
| освободить, не перезапуская | `: > /proc/PID/fd/N` |
| вернуть удалённый открытый файл | `cp /proc/PID/fd/N новый` |
| `No space left`, а место есть | `df -i`, `du --inodes` |
| `ls` и `du` расходятся | разреженный файл: `du --apparent-size` |
| имя не набрать | `ls -i`, `find . -inum N -delete` |
| перенос больших данных между ФС | `cp -a` или `rsync -aHAX`, сверка, потом `rm` |
