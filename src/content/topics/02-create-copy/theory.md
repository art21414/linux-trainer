# Создание и копирование файлов

Создать файл и скопировать каталог умеет каждый, кто прошёл RHCSA. Ошибки начинаются в деталях: `>` вместо `>>` обнуляет конфиг, `cp -r` во второй раз кладёт копию не рядом, а внутрь старой, бэкап сайта теряет `.htaccess`, а копия от root внезапно принадлежит root. Ни одна из этих команд не выдаёт ошибку — поэтому их и не замечают.

В этой главе мы создадим файлы и каталоги всеми ходовыми способами, а потом разберём `cp`: куда ляжет копия, что она унесёт с собой и что станет с файлами, которые уже лежали на месте.

## Пустой файл, > и >> {#create}

`touch` создаёт пустой файл, если его нет. Если файл есть, содержимое не трогается, а время (atime и mtime) становится «сейчас». С `-c` новый файл не создаётся, только обновляется время существующего. Ещё пригодится `touch -r образец файл`: взять время у другого файла.

`>` создаёт файл, а если он уже есть — **обрезает до нуля** и пишет заново. `>>` дописывает в конец. Разница в один символ, и опечатка в `echo ... > /etc/app.conf` стоит конфига. От неё есть защита — `noclobber`:

```text
$ set -o noclobber
$ echo x > report.txt
bash: report.txt: cannot overwrite existing file
$ echo x >| report.txt
```

С ней `>` отказывается перезаписывать существующий файл, `>>` работает как раньше, а `>|` перезаписывает явно, «я знаю, что делаю». Включается на сессию; если вы часто правите конфиги на проде, впишите её в `~/.bashrc`.

Теперь задача из жизни: лог `/var/log/app/debug.log` разросся на весь `/var`, приложение пишет в него не переставая. Первое желание — `rm` и `touch`. Но процесс держит открытым **старый** файл: `rm` убирает имя, а место не освободится, пока процесс жив, и писать он будет в удалённый файл (это разберём в главе про удаление). Правильно — обрезать файл на месте:

```text
$ stat -c '%i %s' debug.log
665497 588895
$ : > debug.log
$ stat -c '%i %s' debug.log
665497 0
```

`:` — пустая команда, которая ничего не выводит, а `>` обрезает файл до нуля. Номер inode (`%i`) тот же, размер (`%s`) — ноль: это тот же файл, и процесс продолжает писать в него. То же делает `truncate -s 0 debug.log`. А `rm` плюс `touch` дают новый файл, о котором приложение не знает, — даже если ядро выдаст ему тот же номер inode: освободившиеся номера раздаются повторно.

## mkdir: -p и -m {#mkdir}

Без ключей `mkdir` создаёт один уровень и ругается, если родителя нет или каталог уже есть:

```text
$ mkdir conf/nginx
mkdir: cannot create directory ‘conf/nginx’: No such file or directory
$ mkdir -p conf/nginx
$ mkdir conf
mkdir: cannot create directory ‘conf’: File exists
$ mkdir -p conf
$ echo $?
0
```

`-p` создаёт всю цепочку и молчит, если каталог уже есть. Поэтому в скриптах пишут `mkdir -p`: повторный запуск не падает. `-v` перечисляет, что создано.

`-m` задаёт права сразу и точно, без учёта umask. Но подвох в том, что только **последнему** каталогу цепочки:

```text
$ mkdir -p -m 700 x/y/z
$ ls -ld x x/y x/y/z
drwxr-xr-x. 3 root root 15 Nov  2 19:09 x
drwxr-xr-x. 3 root root 15 Nov  2 19:09 x/y
drwx------. 2 root root  6 Nov  2 19:09 x/y/z
```

Промежуточные `x` и `x/y` получили обычные права по umask. Для секретов это как раз то, что нужно: закрыт только конечный каталог, а путь к нему остаётся проходимым. А вот `chmod -R 700` на верхний каталог закрыл бы всю ветку.

## Имена с пробелами и дефисом {#names}

Имена чувствительны к регистру, расширение — просто часть имени. Проблемы создают пробелы и дефис.

bash делит строку на слова по пробелам, поэтому `touch my file` создаёт **два** файла: `my` и `file`. Чтобы пробел стал частью имени, его берут в кавычки или экранируют: `"my file"`, `'my file'`, `my\ file`. Больнее всего это бьёт по переменным:

```text
$ touch my file
$ touch "my file"
$ f="my file"
$ ls -l $f
-rw-r--r--. 1 root root 0 Nov  2 19:29 file
-rw-r--r--. 1 root root 0 Nov  2 19:29 my
$ ls -l "$f"
-rw-r--r--. 1 root root 0 Nov  2 19:29 'my file'
```

Без кавычек bash снова разрезал значение, и `ls` показал совсем другие файлы. С `cp $f` или `rm $f` пострадали бы два чужих файла. Правило для скриптов: переменную с путём всегда пишем в кавычках, `"$f"`.

Имя, начинающееся с дефиса, законно, но любая команда примет его за ключи:

```text
$ touch -rf
touch: failed to get attributes of 'f': No such file or directory
$ touch -- -rf
$ touch ./-rf
```

`touch` понял `-rf` как `-r f`: «возьми время у файла `f`». `--` означает «ключи кончились, дальше только имена», а `./-rf` просто не начинается с дефиса.

> **Ловушка.** Кавычки от дефиса не спасают: `touch '-rf'` — то же самое, что `touch -rf`. Кавычки снимает bash ещё до запуска команды, и `touch` всё равно получает строку `-rf`. Кавычки защищают от bash (пробелы, `*`, `$`), а от разбора ключей — только `--` и `./`.

## cp: куда ляжет копия {#cp}

Правила все знают: `cp файл имя` — копия под новым именем, `cp файл каталог/` — внутрь каталога, несколько источников — последним должен быть каталог, каталог копируется только с `-r`. Самое коварное правило — последнее: если цель — **существующий каталог**, источник кладётся **внутрь** него.

Сделаем бэкап сайта дважды одной и той же командой:

```text
$ cp -r site /backup/site
$ ls -A /backup/site
css  .htaccess  index.html
$ cp -r site /backup/site
$ ls -A /backup/site
css  .htaccess  index.html  site
```

В первый раз `/backup/site` не было, и копия стала им. Во второй раз каталог уже был, и копия легла внутрь, в `/backup/site/site`. Старые файлы при этом не обновились. В ночном скрипте бэкапа это бомба замедленного действия: файлы в бэкапе больше не обновляются, а свежая копия каждую ночь пишется в `/backup/site/site`.

Обновить копию правильно можно двумя способами:

```text
$ cp -r site/. /backup/site/
$ cp -rT site /backup/site
```

`site/.` — «содержимое каталога, включая скрытые». `-T` говорит: «цель — это сам каталог назначения, а не место, куда класть». Подумайте, чем плох третий вариант, `cp -r site/* /backup/site/`. Звёздочка не видит скрытых файлов:

```text
$ cp -r site/* stage/
$ ls -A stage
css  index.html
```

`.htaccess` потерялся, и сайт на новом месте молча работает без ограничений доступа.

Что делать с файлами, которые уже лежат в цели? По умолчанию `cp` перезаписывает их молча. Ключи это меняют:

| Ключ | Что делает |
|---|---|
| `-i` | спрашивает `overwrite '...'?`; не `y` — пропуск |
| `-n` | никогда не перезаписывает, молча, код возврата 0 |
| `-u` | копирует, только если источник новее цели |
| `-b` | старую версию сохраняет рядом, с `~` на конце |
| `-v` | печатает, что скопировано |

```text
$ cp -bv src/a.conf dst/a.conf
'src/a.conf' -> 'dst/a.conf' (backup: 'dst/a.conf~')
```

> **Ловушка.** У root в RHEL в `~/.bashrc` есть алиас `cp='cp -i'`, поэтому root на каждую перезапись получает вопрос, а вставленный в терминал скрипт виснет на первом `overwrite?`. `cp -f` вопрос **не отменяет**: у `cp` ключ `-f` означает другое — «если цель не открывается на запись, удали её и попробуй снова». Обойти алиас: `\cp` или `command cp`.

## cp: что унесёт копия {#preserve}

Обычная копия — новый файл. Посмотрим, что от оригинала до неё доживает. root копирует `index.html` от alice (права 640, mtime — май 2024) тремя способами:

```text
$ cp index.html /tmp/c1.html
$ cp -p index.html /tmp/c2.html
$ cp -a index.html /tmp/c3.html
$ ls -l index.html /tmp/c?.html
-rw-r-----. 1 alice alice 12 May  5  2024 index.html
-rw-r-----. 1 root  root  12 Nov  2 19:17 /tmp/c1.html
-rw-r-----. 1 alice alice 12 May  5  2024 /tmp/c2.html
-rw-r-----. 1 alice alice 12 May  5  2024 /tmp/c3.html
```

- Без ключей владелец — тот, кто копирует, mtime — сейчас, права — исходные минус umask. 640 при umask 022 так и остаются 640, а 777 станут 755. Права не «сбрасываются в 644»: umask только убирает биты.
- `-p` — это `--preserve=mode,ownership,timestamps`.
- `-a` — это `-dR --preserve=all`: рекурсивно, символические ссылки копируются ссылками, плюс жёсткие ссылки внутри дерева, xattr и SELinux-контекст. Для бэкапов и переноса деревьев нужен именно `-a`.

Нюанс про обычного пользователя. Отдать файл другому он не может, поэтому `cp -p` от alice молча делает копию её собственной — без ошибки, с кодом 0. Права и время при этом сохраняются:

```text
$ cp -p /tmp/share/bob.txt ~/
$ echo $?
0
$ ls -l ~/bob.txt
-rw-r--r--. 1 alice alice 5 Jan  1  2025 /home/alice/bob.txt
```

Копия **поверх** существующего файла ведёт себя иначе: `cp` не создаёт новый файл, а открывает старый и переписывает содержимое. Inode, владелец и права цели остаются прежними. У `mv` наоборот: под именем оказывается другой inode.

Символические ссылки: `cp ссылка куда` копирует **содержимое** цели и даёт обычный файл, `cp -r` и `cp -a` копируют **саму ссылку**. Относительная ссылка на новом месте часто оказывается битой: `current -> releases/v2`, скопированная в `/srv`, указывает на несуществующий `/srv/releases/v2`. Нужен настоящий каталог — добавляем `-L`.

> **На практике.** Обычный `cp` создаёт новый файл, и тот получает SELinux-контекст каталога назначения. `mv` и `cp -a` уносят исходный. Файл, перенесённый из домашнего каталога в `/var/www/html` через `mv`, останется с типом `user_home_t`, и httpd ответит 403 при правильных правах. Лечит `restorecon -Rv /var/www/html` (подробно — в главе про SELinux).

## Шпаргалка {#cheatsheet}

| Задача | Команда |
|---|---|
| обнулить лог, не меняя inode | `: > file`, `truncate -s 0 file` |
| запретить `>` затирать файлы | `set -o noclobber`, явно — `>|` |
| цепочка каталогов, без ошибки на повтор | `mkdir -p` |
| права только конечному каталогу | `mkdir -p -m 700 a/b/c` |
| имя с дефисом | `touch -- -x`, `touch ./-x` |
| обновить копию каталога | `cp -r src/. dst/`, `cp -rT src dst` |
| не затирать / только новее / с бэкапом | `cp -n` / `cp -u` / `cp -b` |
| сохранить владельца, права, время | `cp -p`; дерево целиком — `cp -a` |
| ссылку как настоящий каталог | `cp -rL` |
