# Inode и ссылки

В прошлых главах мы то и дело упирались в одно слово: `mv` мгновенный, потому что «меняется только запись в каталоге»; место после `rm` не освобождается, потому что «у inode ещё есть ссылки». Пора разобраться, что это такое, — и тогда жёсткие и символические ссылки перестанут быть заучиванием таблицы «чем отличаются».

Сценарий всё тот же: приложение в `/srv/app`, релизы в `releases/`, `current` — ссылка на активный. В конце главы мы научимся переключать её так, чтобы не сломать выкладку.

## Inode: имя отдельно, файл отдельно {#inode}

Файловая система хранит файл в двух частях. **Inode** — служебная запись: тип, права, владелец, размер, времена, число ссылок и адреса блоков с данными. **Блоки** — само содержимое. Одного в inode нет — **имени**. Имя хранится в каталоге: каталог — это таблица «имя → номер inode», и `ls` просто читает её.

```text
$ ls -lia /srv/app   # строки обрезаны
262272 drwxr-xr-x. 4 root  root   91 Nov  2 09:31 .
   128 drwxr-xr-x. 6 root  root   51 Nov  2 19:29 ..
262283 -rw-r--r--. 1 root  root  270 Oct 28 16:40 app.conf
655488 drwxr-xr-x. 4 root  root   26 Nov  2 09:30 releases
```

`.` и `..` — обычные строки таблицы: `.` ведёт на inode самого `/srv/app`, `..` — на inode `/srv`. Отсюда и загадочное число ссылок у каталога. На `releases` ведут: имя `releases` в `/srv/app`, его собственная `.` и `..` в каждом из двух подкаталогов. Итого 4. У пустого каталога всегда 2.

Из того, что имя живёт отдельно от файла, следует всё остальное:

- переименование внутри ФС меняет только строку таблицы — мгновенно, inode тот же;
- удаление убирает строку; inode и данные освобождаются, когда строк не осталось **и** файл никто не держит открытым;
- права на каталог — это права на таблицу имён, поэтому для удаления нужен `w` на каталог;
- номер inode уникален только **внутри одной ФС**.

`ls -l` показывает выборку из inode, а `stat` — всё. Для скриптов удобен формат:

```text
$ stat -c '%i %h %s %U %a %n' run.sh logs
262277 1 42 root 755 run.sh
262274 2 75 alice 755 logs
```

`%i` — номер inode, `%h` — число жёстких ссылок, `%s` — размер, `%U` и `%a` — владелец и права. На ссылку `stat` показывает её саму, `stat -L` идёт к цели.

Inode тоже не бесконечны. Каждому файлу, даже пустому, нужен свой, и если их выгрести, ошибка будет та же, что при нехватке места:

```text
$ touch sessions/s7
touch: cannot touch 'sessions/s7': No space left on device
$ df -h .
Filesystem      Size  Used Avail Use% Mounted on
/dev/loop2       16M  424K   15M   3% /var/spool/app
$ df -i .
Filesystem     Inodes IUsed IFree IUse% Mounted on
/dev/loop2        112   112     0  100% /var/spool/app
```

Места свободно 97 %, а inode — ноль. Виновники обычно миллионы мелких файлов: сессии, почтовая очередь, кеш. У ext4 число inode задаётся при создании ФС и не растёт; XFS, ФС по умолчанию в RHEL 9, выделяет их динамически, поэтому там это редкость. Увидели `No space left on device` при свободном месте — смотрите `df -i`.

## Жёсткая ссылка — второе имя {#hard}

Если имя — просто строка в таблице, то у одного inode может быть несколько имён. Это и есть жёсткие ссылки. Создадим жёсткую и символическую и посмотрим на номера:

```text
$ ln app.conf app.hard
$ ln -s app.conf app.soft
$ ls -li
155 -rw-r--r--. 2 root root 10 Nov  2 19:20 app.conf
155 -rw-r--r--. 2 root root 10 Nov  2 19:20 app.hard
156 lrwxrwxrwx. 1 root root  8 Nov  2 19:20 app.soft -> app.conf
```

`app.conf` и `app.hard` — два имени inode 155, счётчик ссылок стал 2. Ни одно из них не «главное», и запись через одно имя видна через другое — данные-то одни. Теперь переименуем «оригинал»:

```text
$ mv app.conf app.conf.orig
$ cat app.hard
port=8080
$ cat app.soft
cat: app.soft: No such file or directory
```

Жёсткой ссылке всё равно: она указывает на inode, а не на имя. Символическая хранит **путь** `app.conf`, по нему теперь пусто, и она стала битой. С `rm app.conf` было бы то же: данные доступны через `app.hard`, пока счётчик не дойдёт до нуля.

Отсюда практический вывод. Удалили огромный файл, а место не освободилось, и `lsof +L1` пуст? Проверьте счётчик ссылок: где-то осталось второе имя. Найти все имена одного файла можно по номеру inode:

```text
$ find /srv -xdev -inum 155
/srv/links/app.hard
/srv/links/app.conf.orig
```

`-xdev` нужен потому, что номер уникален только внутри одной ФС: на соседнем диске inode 155 — совсем другой файл.

У жёстких ссылок два ограничения, и оба следуют из устройства:

```text
$ ln d d2
ln: d: hard link not allowed for directory
$ ln /srv/links/app.conf /backup/app.conf
ln: failed to create hard link '/backup/app.conf' => '/srv/links/app.conf': Invalid cross-device link
```

На каталоги нельзя, иначе в дереве появились бы циклы, и `find`, `du`, `rm -r` ходили бы по кругу. Между ФС нельзя: номер inode с XFS ничего не значит для ext4 в `/backup`. В обоих случаях выход — символическая ссылка.

## Символическая ссылка — файл с путём {#symlink}

Символическая ссылка — отдельный маленький inode, внутри которого записан путь. Размер ссылки — длина этого пути (`app.conf` — 8 байт). Права у неё всегда `lrwxrwxrwx` и ни на что не влияют: доступ проверяется по цели. Вести она может куда угодно: на каталог, на другую ФС, в никуда.

Главное правило: **относительный путь в ссылке считается от каталога, где лежит ссылка**, а не от того, где мы были, когда её создавали. Самая частая ошибка с `ln -s`:

```text
$ cd /srv/links
$ ln -s app.conf /etc/myapp.conf
$ cat /etc/myapp.conf
cat: /etc/myapp.conf: No such file or directory
```

Ссылка ищет `app.conf` рядом с собой, то есть `/etc/app.conf`. Подумайте, что будет, если имя ссылки совпадёт с целью: `ln -s app.conf /tmp/app.conf`. Ссылка укажет сама на себя:

```text
$ cat /tmp/app.conf
cat: /tmp/app.conf: Too many levels of symbolic links
```

Ядро бросает поиск после 40 переходов. Правильно — абсолютный путь или `ln -sr`: ключ `-r` сам посчитает относительный путь от места ссылки:

```text
$ ln -sr app.conf /etc/myapp3.conf
$ ls -l /etc/myapp3.conf
lrwxrwxrwx. 1 root root 21 Nov  2 19:20 /etc/myapp3.conf -> ../srv/links/app.conf
```

Относительные ссылки хороши, когда дерево переносят целиком: `current -> releases/v2` работает в любой копии `/srv/app`. Абсолютные — когда переносят саму ссылку.

Проверять ссылки в скриптах нужно правильным ключом. `readlink -f` выдаёт канонический путь, даже если последнего компонента нет, — для битой ссылки код возврата будет 0. `readlink -e` требует, чтобы существовало всё:

```text
$ readlink -f /etc/myapp.conf; echo $?
/etc/app.conf
0
$ readlink -e /etc/myapp.conf; echo $?
1
```

Битые ссылки ищет `find -xtype l` — «после разыменования это всё ещё ссылка», то есть цель не найдена:

```text
$ find /etc -maxdepth 1 -xtype l
/etc/myapp.conf
```

## Переключаем current {#switch}

Выкладка через `current` удобна тем, что переключение — это смена одной ссылки. Переключим на `v3` «очевидной» командой:

```text
$ ln -sf releases/v3 current
$ ls -l current
lrwxrwxrwx. 1 root root 11 Nov  2 09:31 current -> releases/v2
$ ls releases/v2
bin  conf  install.log  v3
```

Ничего не переключилось, зато внутри `releases/v2` появилась ссылка `v3`. Если последний аргумент — ссылка на каталог, `ln` (как `cp` и `mv`) считает его каталогом и кладёт новую ссылку внутрь. Ключ `-n` велит не разыменовывать цель:

```text
$ ln -sfn releases/v3 current
$ ls -l current
lrwxrwxrwx. 1 root root 11 Nov  2 19:41 current -> releases/v3
```

`ln -sfn` (или `ln -sfT`) — правильный способ переключать такие ссылки.

С удалением та же история со слэшем. Хотели убрать ссылку `previous` на старый релиз, но по привычке дописали слэш:

```text
$ rm -r previous/
rm: cannot remove 'previous/': Not a directory
$ ls releases/v1
```

Ошибка выглядит как неудача, но ущерб уже нанесён. Слэш на конце заставляет пройти по ссылке: `rm -r` спустился в `releases/v1`, удалил всё содержимое и только в конце попытался удалить сам `previous/` — а это ссылка. Ссылка осталась, релиз пуст.

> **Ловушка.** Ссылку удаляют **без** слэша: `rm previous` или `unlink previous`. `ls -l current/`, `rm -r current/`, `cp -r current/` работают с тем, что за ссылкой, а без слэша — с самой ссылкой.

## Шпаргалка {#cheatsheet}

| | Жёсткая (`ln`) | Символическая (`ln -s`) |
|---|---|---|
| Что это | ещё одно имя того же inode | отдельный файл с путём |
| На каталог / на другую ФС | нельзя / нельзя | можно / можно |
| Цель переименовали или удалили | данные живы | ссылка битая |
| Как увидеть | счётчик > 1, один номер в `ls -i` | `l` и `->` в `ls -l` |

| Задача | Команда |
|---|---|
| все имена файла | `find /fs -xdev -inum $(stat -c %i файл)` |
| inode кончились? | `df -i` |
| ссылка, переживающая перенос дерева | `ln -sr цель ссылка` |
| ссылка жива? | `readlink -e` (не `-f`) |
| битые ссылки | `find … -xtype l` |
| переключить ссылку на каталог | `ln -sfn новая current` |
| удалить ссылку | `rm link` без слэша, `unlink link` |
