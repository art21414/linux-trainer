# Перемещение, переименование, удаление

`mv` и `rm` кажутся самыми простыми командами, и именно поэтому их набирают не думая. А потом выкладка ложится не на место, а внутрь старого каталога, `rm *` сносит то, что трогать было нельзя, а удалённый лог продолжает занимать весь диск.

В этой главе разберём, что `mv` и `rm` делают на самом деле. Оба работают не с данными, а с **записями в каталоге** — именами. Из этого следует почти всё: почему переименование мгновенное, почему для удаления нужны права на каталог и почему место после `rm` иногда не освобождается.

## mv: переименование и перенос {#mv}

Каталог — это таблица «имя → номер inode», а сам файл (данные, права, владелец) живёт в inode. Подробно про inode — в следующей главе, здесь нам хватит этой картинки. Внутри одной файловой системы `mv` вызывает `rename()`: переписывает строку в таблице и данные не трогает. Поэтому 50-мегабайтный дамп переименовывается так же мгновенно, как пустой файл:

```text
$ ls -li dump.sql
262294 -rw-r--r--. 1 root root 52428800 Oct 30 03:00 dump.sql
$ mv -v dump.sql dump-old.sql
renamed 'dump.sql' -> 'dump-old.sql'
$ ls -li dump-old.sql
262294 -rw-r--r--. 1 root root 52428800 Oct 30 03:00 dump-old.sql
```

Номер inode тот же, mtime тот же: содержимое никто не трогал. Меняется только ctime файла и время каталога, в котором поменялась таблица.

Теперь перенесём дамп на `/backup` — это другой диск. Номер inode имеет смысл только внутри своей ФС, поэтому переименовать между ФС нельзя. Ядро отвечает `EXDEV`, и `mv` молча переходит к плану Б: копирует и удаляет оригинал. `-v` это выдаёт:

```text
$ mv -v dump-old.sql /backup/
copied 'dump-old.sql' -> '/backup/dump-old.sql'
removed 'dump-old.sql'
```

Вместо `renamed` — `copied` и `removed`. Значит, время работы пропорционально размеру, на цели нужно место под полную копию, а владельца, права и время `mv` переносит, как `cp -a`. Подумайте, что будет, если такой `mv` каталога на сотни гигабайт оборвётся на середине. Источник удаляется только после того, как скопировано всё дерево. Обрыв во время копирования оставит целый источник и неполную копию. Обрыв во время удаления — полную копию и обрывки источника. Поэтому большие данные между дисками переносят в два шага: `cp -a` (или `rsync -a`), сверка, потом `rm`.

Куда ляжет источник — правила те же, что у `cp`: если цель — существующий каталог, источник уйдёт **внутрь**. На выкладке это классика:

```text
$ mv /srv/build /var/www/html
```

Если `/var/www/html` уже есть, новая сборка окажется в `/var/www/html/build`, а сайт продолжит отдавать старую версию. Правильно — сначала убрать старое (`mv /var/www/html /var/www/html.old`), потом переименовать новое. `-T` велит считать цель самим каталогом. Каталог поверх **непустого** каталога `mv` не положит вовсе. Текст ошибки зависит от ФС:

```text
mv: cannot move '/srv/a2/dir' to '/srv/b2/dir': File exists
mv: cannot move '/backup/a/dir' to '/backup/b/dir': Directory not empty
```

Первая строка — с XFS, вторая — с ext4. Ключи `-i`, `-n`, `-u`, `-b`, `-v` работают как у `cp`. Одно отличие: у `mv` ключ `-f` отменяет `-i`, в том числе из алиаса root `mv='mv -i'`.

**Массовое переименование.** `mv *.txt *.csv` не работает: `mv` получает список вида `a.txt b.txt *.csv` и требует, чтобы последний аргумент был каталогом:

```text
$ mv *.txt *.csv
mv: target '*.csv' is not a directory
```

Переименовывают циклом. `${f%.txt}` отрезает от значения суффикс `.txt`, кавычки спасают имена с пробелами, `--` — имена с дефисом:

```bash
for f in *.txt; do
  mv -- "$f" "${f%.txt}.csv"
done
```

В RHEL есть ещё `rename` из util-linux: `rename .txt .csv *.txt`. Perl-версия с синтаксисом `rename 's/…/…/'` из Debian здесь не работает.

## rm: удаляется имя {#rm}

`rm` вызывает `unlink()` — убирает строку «имя → inode» из каталога. Отсюда главное следствие: право на удаление определяется правами на **каталог** (нужны `w` и `x`), а не на файл. alice удалит файл root в своём домашнем каталоге (`rm` только переспросит), но не удалит свой собственный файл в каталоге, куда ей нельзя писать:

```text
$ rm -v ~/root.conf
rm: remove write-protected regular file '/home/alice/root.conf'? y
removed '/home/alice/root.conf'
$ rm /srv/shared/alice.txt
rm: cannot remove '/srv/shared/alice.txt': Permission denied
```

Вопрос про write-protected задаётся, только если удаляет не root и стандартный ввод — терминал. В cron и в пайпе файл удалится молча.

С каталогами `rm` работает только по явной просьбе:

```text
$ rm dir
rm: cannot remove 'dir': Is a directory
$ rmdir dir
rmdir: failed to remove 'dir': Directory not empty
```

`rmdir` (и `rm -d`) удаляет только **пустые** каталоги. Это удобная страховка: если внутри что-то осталось, ничего не пропадёт. `rm -r` удаляет дерево целиком, `rmdir -p a/b/c` — цепочку пустых каталогов снизу вверх.

Ключи вопросов:

| Ключ | Что делает |
|---|---|
| `-f` | ничего не спрашивает; нет файла — не ошибка, код 0 |
| `-i` | спрашивает про каждый файл |
| `-I` | спрашивает один раз: больше трёх файлов или `-r` |

Ключи действуют по принципу «последний побеждает». Алиас root `rm='rm -i'` превращает `rm -rf dir` в `rm -i -rf dir`, и `-f` отменяет вопросы. Так что алиас защищает от `rm файл`, но не от `rm -rf`.

Корзины нет. И `rm` не затирает данные, а только освобождает блоки — для уничтожения есть `shred`, но на журналируемых ФС и SSD гарантий не даёт и он.

## Опасные аргументы: дефис, звёздочка, пустая переменная {#danger}

Загрузчик с багом создал файл `-rf`. Удалим его в лоб:

```text
$ rm -rf
$ ls
a.txt  logs  -rf
```

Ничего не произошло, даже ошибки нет: `rm` понял `-rf` как ключи, а `-rf` без имён — законная команда. Кавычки не помогут, их снимает bash. Работают `rm -- -rf` и `rm ./-rf`.

Теперь страшное: что сделает `rm *` в этом каталоге? Посмотрим через `echo`, во что раскроется шаблон:

```text
$ echo rm *
rm a.txt logs -rf
```

GNU `rm` понимает ключи в любом месте строки, так что это `rm -rf a.txt logs`. Удалится всё, **кроме** самого `-rf`, и каталог `logs` — рекурсивно. Алиас `rm -i` не спасёт: `-f` из имени отменит вопросы. Безопасно — `rm ./*` или `rm -- *`: имя уже не может стать ключом.

> **На практике.** В каталоги, куда пишут внешние клиенты (загрузки, почта, выгрузки), попадают любые имена. Чистите их через `./*`, `--` или `find … -delete`, которому имена безразличны.

Пустая переменная — вторая классика:

```bash
DIR=
rm -rf "$DIR"/     # станет rm -rf /
rm -rf "$DIR"/*    # станет rm -rf /bin /boot …
```

Первую строку остановит встроенная защита `--preserve-root`:

```text
rm: it is dangerous to operate recursively on '/'
rm: use --no-preserve-root to override this failsafe
```

Вторую — нет: звёздочка раскроется в `/bin /boot /dev …`, и ни один аргумент не равен `/`. Защита — `"${DIR:?}"/*`: при пустой переменной bash остановится с `DIR: parameter null or not set` ещё до запуска `rm`. `set -u` тут не поможет: он ловит только **незаданные** переменные, а `DIR=` задана, просто пуста.

## Удалил, а место не освободилось {#deleted-open}

Блоки возвращаются ФС, только когда у файла не осталось ни одного имени **и** его не держит открытым ни один процесс. Отсюда главный ночной сюрприз. `/srv` заполнен, виновник — `debug.log` на 150 МБ. Удаляем:

```text
$ rm /srv/app/logs/debug.log
$ df -h /srv
Filesystem      Size  Used Avail Use% Mounted on
/dev/loop0      236M  183M   54M  78% /srv
$ du -sh /srv
2.4M    /srv
```

Файла нет, `du` насчитал 2,4 МБ, а `df` по-прежнему видит 183 МБ. `rm` убрал имя, но приложение держит файл открытым и пишет в него. `du` обходит имена и такого файла не видит, а `df` спрашивает ФС о занятых блоках. Расхождение `df` и `du` — главный симптом.

Кто держит удалённые файлы, показывает `lsof +L1` — «открытые файлы, у которых меньше одной ссылки»:

```text
$ lsof +L1
COMMAND  PID USER   FD   TYPE DEVICE  SIZE/OFF NLINK   NODE NAME
myapp   1916 root    3w   REG    7,0 157286400     0 262290 /srv/app/logs/debug.log (deleted)
```

`NLINK 0` — имён нет, `FD 3w` — дескриптор 3 открыт на запись. Каждый дескриптор процесса виден как ссылка `/proc/PID/fd/N`, и через неё можно добраться до удалённого файла. Как освободить место:

1. Правильно — перезапустить сервис (`systemctl restart`) или попросить его переоткрыть логи. Процесс закроет дескриптор, ядро освободит блоки.
2. Если перезапускать нельзя — обрезать файл через дескриптор: `: > /proc/1916/fd/3`. Запись идёт в тот самый удалённый файл, и `df` сразу показывает свободное место.

У этого есть и приятная сторона. Если по ошибке удалили конфиг, а долгоживущий процесс ещё держит его открытым, содержимое можно достать: `cp /proc/1971/fd/3 /srv/app/app.conf`. Получится новый файл — права, владельца и SELinux-контекст вернёте руками. Работает, только пока процесс жив.

> **Важно.** Лог, в который пишет живой процесс, чистят через `: > app.log` или `truncate -s 0`, а не через `rm`. Тогда файл остаётся тем же, и место освобождается сразу.

## Шпаргалка {#cheatsheet}

| Задача | Команда |
|---|---|
| переименовать / видеть, что сделано | `mv -v` (`renamed` — rename, `copied`+`removed` — между ФС) |
| заменить каталог, а не положить внутрь | убрать старый, потом `mv`; или `mv -T` |
| массово сменить расширение | `for f in *.txt; do mv -- "$f" "${f%.txt}.csv"; done` |
| удалить, только если пусто | `rmdir`, `rm -d` |
| удалить файл `-rf` | `rm -- -rf`, `rm ./-rf` |
| чистить каталог с чужими именами | `rm ./*`, `find … -delete` |
| защита от пустой переменной | `rm -rf "${DIR:?}"/*` |
| кто держит удалённые файлы | `lsof +L1`, `ls -l /proc/PID/fd` |
| освободить место без рестарта | `: > /proc/PID/fd/N` |
| вернуть удалённый, пока открыт | `cp /proc/PID/fd/N файл` |
