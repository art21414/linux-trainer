# Чтение файлов

Дежурный прислал архив с логами сборщика событий. По его словам, последний запуск закончился ошибкой, а выгрузка содержит на одну запись меньше, чем ожидали. Разберём оба симптома. Сначала посмотрим, какие байты в конфиге, затем вытащим нужные строки из файлов и проверим, что именно посчитали.

## Когда обычного cat мало {#visible}

Конфиг небольшой, его можно показать целиком. Но с виду одинаковые строки могут содержать разные байты. Допустим, сборщик получил файл, сохранённый в Windows. Сделаем короткий пример с той же особенностью и посмотрим его через `cat -A`:

```bash
$ printf 'mode=prod\r\n\tport=8080\r\nready' > cfg
$ cat -A cfg; echo
mode=prod^M$
^Iport=8080^M$
ready
```

`^I` обозначает табуляцию, `^M` — возврат каретки `\r`, а `$` отмечает перевод строки `\n`. Первые две строки заканчиваются парой `\r\n` (CRLF). У последней строки отметки нет. Дополнительный `echo` в примере отделяет приглашение оболочки от вывода: сам файл заканчивается на `y`.

Если файл попал на Linux как скрипт, возврат каретки в строке `#!/bin/bash` может превратить имя интерпретатора в `/bin/bash\r`. Отсюда ошибка о неизвестном интерпретаторе, хотя `/bin/bash` на месте. Для диагностики полезно сохранить отображение через `cat -A cfg > cfg.visible`, оставив входной файл без изменений. Если важны только концы строк, есть `cat -E`. Обычный `cat` лишь передаёт байты дальше, поэтому копия через него тоже сохранит оба управляющих символа.

У незнакомого вложения сначала посмотри тип через `file`. Например, расширение `.log` могли оставить после сжатия. `file` смотрит на данные и метаданные, а не выбирает формат по расширению. Если входной файл — текст, `cat` подойдёт для короткого куска. Для большой выгрузки лучше сразу сузить просмотр.

## Взять начало, конец или диапазон {#slice}

У лога начало рассказывает, с каким конфигом запустился процесс. Конец хранит последние сообщения перед остановкой. Для обоих случаев необязательно выводить файл целиком. Пусть в учебном логе такую последовательность из четырёх букв заменяют четыре события:

```bash
$ printf 'A\nB\nC\nD\n' > nodes.log
$ head -n 2 nodes.log
A
B
$ tail -n 2 nodes.log
C
D
```

Теперь задача немного меняется. В выгрузке последняя строка — служебная сводка, а нужны все записи до неё. Сколько записей в файле, заранее неизвестно. `head -n -1` оставит всё до последней строки. Если первая строка — заголовок, `tail -n +2` начнёт со второй и выведет всё до конца. Знак связан с тем, откуда идём: `head` исключает строки в хвосте, `tail` с плюсом начинает с заданного номера.

Для выборки с 2-й по 3-ю строку можно отрезать всё после третьей и отбросить первую из оставшихся:

```bash
$ head -n 3 nodes.log | tail -n +2
B
C
```

Если диапазон известен, тот же кусок печатает `sed -n '2,3p' nodes.log`. У `head` и `tail` есть и режим байтов `-c`. Он пригодится, например, когда диагностический файл имеет маркер фиксированной длины. Помни про UTF-8: короткая выборка по байтам может обрезать символ посередине. Для логов с текстом надёжнее отбирать целые строки.

Когда передаёшь несколько файлов, `head` и `tail` подписывают каждый кусок. Если склеиваешь строки для обработки, подписи можно отключить ключом `-q`:

```bash
$ printf 'X\nY\n' > backup.log
$ head -q -n 1 nodes.log backup.log
A
X
```

Порядок аргументов определяет порядок кусков. В отчёте для человека подписи помогают понять, из какого файла взята каждая строка, а в машиночитаемом отчёте лишние строки легко принять за записи.

## Почему счётчики расходятся {#count}

В конфиге из первого опыта глаз видит три строки. Сравним это с показаниями утилиты:

```bash
$ wc -l cfg
2 cfg
$ wc -l < cfg
2
```

`wc -l` считает байты перевода строки LF. После `ready` такого байта нет, а значит, в счётчике окажутся только два CRLF. Саму последнюю запись всё ещё можно прочитать через `tail -n 1 cfg`. Если это выгрузка для импорта, сначала установи, что требует формат: для одних потребителей отсутствие последнего LF допустимо, для других файл с такой концовкой надо считать повреждённым.

Второй вызов полезен для отчётов. При `< cfg` файл открывает оболочка и даёт `wc` стандартный ввод. Имя файла не попадает в вывод. При нескольких аргументах `wc` выдаёт отдельную строку на каждый файл и итоговую строку. Итог удобен на экране, но при записи ответа стоит сперва решить, нужен общий счётчик или значения с разбивкой.

Ещё два счётчика легко спутать. `-c` считает байты, а `-m` в UTF-8-локали — символы по правилам этой кодировки. Проверим на одной кириллической букве и одном LF:

```bash
$ export LC_ALL=C.utf8
$ printf 'я\n' > note.txt
$ wc -lmc < note.txt
1 2 3
```

Результат расположен в порядке «переводы строк, символы, байты», хотя ключи можно передать в другом порядке. Два байта у буквы плюс один у перевода строки. Флаг `-w` нужен для счёта слов по пробельным разделителям, но таким способом нельзя посчитать поля CSV с кавычками.

> **Ловушка.** `wc -L` меряет ширину самой длинной строки на экране. Например, `a\tb` занимает 9 колонок: `a` стоит в первой, табуляция переносит позицию на девятую, затем печатается `b`. Это отдельный счётчик, отличный от длины строки в байтах.

## Длинный файл и живой журнал {#follow}

У длинного лога обычно нужно прочитать несколько соседних сообщений вокруг ошибки. На сервере удобно открыть `less app.log`: поиск вперёд — `/текст`, следующее совпадение — `n`, к началу и концу файла ведут `g` и `G`, выход — `q`. Ключ `-S` отключает перенос широких строк. Для передачи небольшого куска коллеге я всё равно сохраню выборку через `head`, `tail` или `sed`, чтобы можно было сравнить файлы и проверить их автоматически.

Если процесс продолжает писать в лог, снимок конца быстро устареет. `tail -f app.log` открывает файл и ждёт новых строк. После ротации старый `app.log` могут переименовать в `app.log.1` и создать новый под исходным именем. Дескриптор, открытый до переименования, всё ещё указывает на старый файл. Поэтому `tail -f` может замолчать: процесс уже пишет в новый файл, а читатель остался на старом.

> **На практике.** Если путь должен пережить такую ротацию, запусти `tail -F app.log`. Ключ означает `--follow=name --retry`: при замене файла утилита переоткроет путь, а при временном исчезновении продолжит попытки. Оба режима можно закончить через `Ctrl+C`.

На одном сервере могут использовать совсем другую ротацию: содержимое копируют в архив и обрезают исходный файл на месте. В этом случае inode обычно сохраняется. Когда отладка идёт по историческим логам, проще сразу открыть конкретный архив и извлечь нужный диапазон. В тренажёре для практики используем снимки файлов: постраничный просмотр и ожидание новых событий разберём на примере поведения реальных команд.

## Шпаргалка {#cheatsheet}

| Задача | Команда |
|---|---|
| Показать табы, CR и переводы строк | `cat -A cfg` |
| Прочитать начало или конец | `head -n 5 log` / `tail -n 5 log` |
| Отбросить заголовок | `tail -n +2 list.csv` |
| Отбросить последнюю строку | `head -n -1 list.csv` |
| Убрать заголовки с именами | `head -q -n 1 a.log b.log` |
| Получить число LF без имени | `wc -l < list.csv` |
| Сравнить символы и байты | `wc -mc < note.txt` |
| Читать с поиском | `less log` |
| Следить за путём через ротацию | `tail -F app.log` |
